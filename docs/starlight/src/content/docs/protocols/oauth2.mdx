# OAuth 2.0

## Standards

- RFC 6749 -- OAuth 2.0 Authorization Framework
- RFC 7636 -- Proof Key for Code Exchange (PKCE)
- RFC 8628 -- Device Authorization Grant
- RFC 7662 -- Token Introspection
- RFC 7009 -- Token Revocation
- RFC 7523 §2.2 -- JWT Profile for OAuth 2.0 Client Authentication
- RFC 7517 -- JSON Web Key Sets
- RFC 8414 -- Authorization Server Metadata
- RFC 9068 -- JWT Profile for OAuth 2.0 Access Tokens
- RFC 8707 -- Resource Indicators for OAuth 2.0
- RFC 9449 -- OAuth 2.0 Demonstrating Proof of Possession (DPoP), opt-in
- RFC 9700 -- OAuth 2.0 Security Best Current Practice

## Available Flows

| Flow ID | Name | Description |
|---------|------|-------------|
| `authorization_code` | Authorization Code | Standard redirect-based authorization |
| `authorization_code_pkce` | Authorization Code + PKCE | Authorization code with code verifier/challenge |
| `client_credentials` | Client Credentials | Machine-to-machine issuance with independent selectors for `client_secret_basic` or `private_key_jwt` authentication and Bearer or DPoP access-token protection |
| `refresh_token` | Refresh Token | Token renewal without re-authorization |
| `implicit` | Implicit Grant (Legacy) | RFC 6749 §4.2: access token in the redirect fragment, no refresh token. RFC 9700 §2.1.2 says clients SHOULD NOT use it |
| `device_code` | Device Authorization | RFC 8628 grant for TVs, CLIs, and other input-constrained devices; person authorizes on a second device |
| `token_introspection` | Token Introspection | Validate and inspect active tokens (RFC 7662) |
| `token_revocation` | Token Revocation | Invalidate tokens (RFC 7009) |

The implicit grant is implemented for the public `public-app` client so the fragment response can be compared with authorization code + PKCE. RFC 9700 §2.1.2: "Clients SHOULD NOT use the implicit grant." The authorization server returns `access_token` and `token_type` in the redirect fragment and does not issue a refresh token. Confidential clients receive `unauthorized_client`. `grant_type=implicit` is not accepted at the token endpoint.

`S256` is the only PKCE transformation `/oauth2/authorize` supports. A `code_challenge` sent with `code_challenge_method=plain`, or with no `code_challenge_method` (which RFC 7636 Section 4.3 defines as `plain`), is refused with `invalid_request` (RFC 7636 Section 4.4.1). RFC 9700 §2.1.1 on methods that keep the verifier out of the authorization request: "Currently, S256 is the only such method."

Resource Owner Password Credentials (`grant_type=password`) is not implemented. RFC 9700 §2.4: "The resource owner password credentials grant MUST NOT be used." Use authorization code + PKCE instead.

## `private_key_jwt` client authentication

The Client Credentials Looking Glass flow can authenticate with a signed JWT
instead of a shared client secret. Select **private_key_jwt** in the flow
configuration, run the flow, then choose **client assertion** in the token
inspector to inspect the real JWT sent to the token endpoint. [Open the Client
Credentials flow](https://protocolsoup.com/looking-glass?protocol=oauth2&flow=client_credentials).

The browser generates an RS256 key with WebCrypto. Its private `CryptoKey` is
non-extractable and never leaves the client; only the public JWK is registered
with the demo authorization server. The start-demo response returns a 256-bit
owner capability; full session access, WebSocket streaming, and public-key
registration require it. Registration is active-session-only and atomically
one-shot. It creates the real session-isolated `client_id` (there is no seeded
`private_key_jwt` client), expires that registration after 10 minutes, and
returns the authorization server's exact token endpoint. Split deployments
therefore use the same `aud` value the server validates, and concurrent
demonstrations cannot replace each other's keys. The server also supports
registered ES256 (P-256) and EdDSA (Ed25519) client keys.

ProtocolSoup applies this deterministic RFC 7523 profile:

- `client_id` is required in the request body and must exactly equal both
  `iss` and `sub`.
- `aud` must contain the exact configured token endpoint URL. A trailing slash
  changes the value and fails validation.
- `iat`, `exp`, and `jti` are required; optional `nbf` is enforced. RFC 7519
  fractional NumericDate values retain nanosecond precision. The assertion
  lifetime is at most 300 seconds, with 60 seconds of clock-skew tolerance.
- `jti` is single-use through the complete acceptance window, including the
  60-second expiration-skew allowance. Development and tests use an in-memory
  reservation store. Demo and production deployments require shared Redis and
  perform one atomic `SET NX` reservation keyed by a hash of `(client_id, jti)`;
  production Redis connections must use `rediss://`.
  Replay-store failures fail closed with `server_error`; assertion validation
  failures continue to use generic `invalid_client` responses.
- Allowed algorithms are RS256, ES256, and EdDSA. The registered key type must
  be RSA, EC P-256, or Ed25519 respectively. If `key_ops` is present it must
  permit `verify`, and the client registration must select `private_key_jwt`.
  RSA moduli must be odd and at least 2048 bits; exponents must be odd, at
  least 3, and safely representable by the verifier.
- Static JWKS keys are checked before an optional HTTPS `jwks_uri`. Remote
  retrieval bypasses environment proxies, rejects IANA special-use IPv4 and
  IPv6 addresses during both DNS validation and dialing, applies one 3-second
  deadline to DNS, connection, TLS, and response reading, rejects redirects,
  caps responses at 64KB, caches for 10 minutes, coalesces concurrent initial
  and forced fetches, and rate-limits refreshes caused by unknown `kid` values.
  Unsupported or malformed unrelated remote keys are ignored when at least one
  usable verification key remains.
- Static, remote, and demo JWKS registrations reject every private JWK member:
  `d`, `p`, `q`, `dp`, `dq`, `qi`, `oth`, and `k`. Rejected registration
  captures redact those values before Looking Glass persistence.
- Assertion validation failures return the same `invalid_client` description.
  Specific reasons appear only in owner-visible Looking Glass history.

This method is intentionally scoped to `client_credentials`. JWT Bearer
authorization grants (RFC 7523 §2.1), `client_secret_jwt`, mTLS, and
certificate-in-header key delivery are separate mechanisms and are not enabled
by this flow.

## Sender-constrained tokens (RFC 9449 DPoP)

The token endpoint accepts an optional `DPoP` proof header
(`htm=POST`, `htu` the exact `/oauth2/token` URL). When present and valid,
the issued access token is bound to the proof's key: it carries a `cnf.jkt`
claim (the RFC 7638 thumbprint of the proof's public key) and the response's
`token_type` is `DPoP` instead of `Bearer`. Absent that header, every existing
Bearer flow is unchanged -- DPoP is opt-in, never mandatory, on this endpoint.

- For the `authorization_code` grant, a DPoP-bound access token issued to a
  **public** client also binds the issued refresh token to the same key
  (RFC 9449 Section 5). A subsequent `refresh_token` request from that
  client must re-present a matching proof; a mismatched or missing proof is
  rejected with `invalid_grant`. A refresh token issued without DPoP does
  not gain binding on refresh even if a proof is later presented. A
  **confidential** client's refresh token is never bound this way, even
  when the token request that issued it carried a valid proof: it is
  already sender-constrained by its client authentication credentials, per
  the spec's own carve-out -- only its *access* token gets `cnf.jkt`.
- The `DPoP` header field itself must not repeat: a request carrying more
  than one is rejected outright rather than silently using the first one
  and ignoring the rest.
- Proof validation rejects `alg: none`, symmetric algorithms, a `jwk` header
  carrying private key material, an `htu`/`htm` mismatch, a stale or future
  `iat` (60-second window), and a replayed `jti` -- replay-store outages fail
  the request closed with `server_error`, never open.
- A server-provided nonce challenge (`DPoP-Nonce` response header,
  `use_dpop_nonce` error) runs at `/oauth2/token` when
  `SHOWCASE_DPOP_NONCE_REQUIRED` is set (RFC 9449 Section 8), and as a
  separate nonce space at `/oauth2/resource` when
  `SHOWCASE_DPOP_RESOURCE_NONCE_REQUIRED` is set (Section 9). Both are on in
  the hosted deployment at protocolsoup.com, so the DPoP flow there always
  shows the challenge and the retry with the supplied nonce. Both default to
  off for local and self-hosted runs. See [Environment
  Variables](/deploy/environment-variables/).
- Only JWT access tokens can be bound. Opaque/reference access token binding
  is a separate mechanism this platform does not implement.
- The RFC 8414 metadata endpoint lists the accepted DPoP proof algorithms
  under `dpop_signing_alg_values_supported` (RFC 9449 Section 5.1).

Run the **Client Credentials** flow in Looking Glass and select **DPoP** under
**Access-token protection** to see a real browser-generated ES256 key produce a
proof. The resulting bound token is rendered distinctly (amber, lock icon) from
a plain Bearer token in the token inspector. Client authentication is a separate
selector, so all four real combinations of `client_secret_basic` or
`private_key_jwt` with Bearer or DPoP can be inspected without switching flows.

RFC 8414 requires an HTTPS issuer. Because protocol routes are mounted at the
origin root, `SHOWCASE_BASE_URL` must be a pathless HTTPS origin in production
(for example `https://as.example`, not `https://as.example/base` or a trailing
slash). The metadata endpoint returns `503` when it cannot derive that issuer.
A loopback HTTP origin (`localhost`, `127.0.0.1`, `[::1]`) is the one
exception, for local development: access tokens name the issuer in `iss`, and
a resource server has to be able to read that issuer's metadata.

## Access tokens (RFC 9068)

Every access token this authorization server issues is a JWT that follows the
JWT Profile for OAuth 2.0 Access Tokens:

| Part | Value |
|------|-------|
| `typ` header | `at+jwt` (RFC 9068 §2.1) |
| `iss` | `{base}/oauth2`, the `issuer` of this server's RFC 8414 metadata |
| `aud` | The protected resource the token is for: `{base}/oauth2/resource`, or `SSF_RESOURCE` for `ssf.read` / `ssf.manage` |
| `sub` | The End-User, or the client for `client_credentials` (RFC 9068 §2.2) |
| `client_id` | The client that requested the token (RFC 8693 §4.3) |
| `exp`, `iat`, `nbf`, `jti`, `scope` | Lifetime, identifier and granted scope |
| `cnf.jkt` | Present on a DPoP-bound token (RFC 9449 §6.1) |

The authorization server issues each access token for one resource. A request
may name it with the `resource` parameter (RFC 8707 §2) at `/oauth2/authorize`,
`/oauth2/device/authorize` or `/oauth2/token`; without one, the scope decides
(RFC 9068 §3). The request is refused with `invalid_target` when `resource` is
not an absolute URI without a fragment, names a resource this server does not
issue tokens for, or does not fit the requested scope. A scope that mixes
`ssf.*` with other values and names no resource is refused with
`invalid_scope`.

`/oauth2/resource` validates a token the way RFC 9068 §4 lists: the `typ`
header, `iss` equal to `{base}/oauth2`, `aud` containing its own URL, the
signature and `exp`. Any failure answers `401` with `invalid_token`. An ID
Token, a refresh token, a token from the OpenID Provider or a token issued for
another resource is therefore refused.

## What To Validate

- PKCE code_challenge and code_verifier alignment
- Token header and claims: `typ` is `at+jwt`; `iss`, `sub`, `aud`,
  `client_id`, `exp`, `iat`, `jti`, `scope`
- Audience: an access token's `aud` is the protected resource it is for and
  its `client_id` claim names the client that requested it. `/oauth2/resource`
  answers `401` with `invalid_token` for a token whose `aud` does not name it
  (RFC 9068 §4), so a token issued for another resource, such as an SSF
  stream-management token, is refused there.
- Introspection response: `active`, `token_type`, `scope`, and `aud` and
  `client_id` reported separately (RFC 7662 §2.2).
- Introspection caller: the endpoint requires authorization (RFC 7662 §2.1),
  which this server takes as client authentication with a client password,
  over HTTP Basic or as `client_id` and `client_secret` in the body. The
  authorization server metadata lists both under
  `introspection_endpoint_auth_methods_supported`. A public client such as
  `public-app` has no credential, so a request that only names its `client_id`
  is refused with `invalid_client` (RFC 6749 §2.3). An authenticated caller is
  told a token is active only when it is the client the token was issued to,
  or a resource server the token's `aud` names (RFC 7662 §4). Any other caller
  receives `{"active": false}` and nothing else. The token being introspected
  is not accepted as the caller's own credential. Looking Glass runs the flow
  as `machine-client` over HTTP Basic, so it reports a Client Credentials
  token as active and a token issued to `public-app` as not active.
- Failed client authentication: `invalid_client`. At `/oauth2/token`,
  `/oauth2/revoke` and `/oauth2/device/authorize` the status is `401` with
  `WWW-Authenticate: Basic realm="oauth2"` when the client used the
  `Authorization` header, and `400` when the credentials were in the body (RFC
  6749 §5.2). `/oauth2/introspect` answers `401` for any invalid client
  credentials (RFC 7662 §2.3), and `400` only for a request with no
  credentials and no `Authorization` header. A client that used another
  scheme than Basic gets a second `WWW-Authenticate` field after the Basic
  one, "matching the authentication scheme used by the client" (RFC 6749
  §5.2): `Bearer realm="oauth2"` for Bearer, and the scheme name alone for
  any other scheme that is an RFC 9110 token. Only `/oauth2/introspect` adds
  `error="invalid_token"` to the Bearer challenge (RFC 7662 §2.3, RFC 6750
  §3).
- Revocation: the server revokes a token only for the client it was issued
  to (RFC 7009 §2.1). A confidential client authenticates with its client
  password, or with a `private_key_jwt` assertion when it registered a key
  (RFC 7523 §2.2; `aud` is the issuer identifier or the token endpoint URL,
  and an unusable replay store answers `503` without revoking); a public
  client such as `public-app` sends `client_id`. The
  response is `200` when the token was revoked and when the submitted value
  is not a live token (RFC 7009 §2.2). A token issued to another client is
  refused with `400` `invalid_grant` and stays valid. RFC 7009 names no code
  for that refusal and takes the error from RFC 6749 §5.2, where
  `invalid_grant` covers a refresh token that "was issued to another client";
  no §5.2 code covers an access token by its words, so the same code is used
  for it, and for an access token issued to no identified client. A valid JWT
  of this server that is neither a refresh token nor an access token, such
  as an ID Token, is refused with `400` `unsupported_token_type` (RFC 7009
  §2.2.1). Revoking a refresh
  token also revokes the unexpired access tokens of the same authorization
  grant, through every rotation (RFC 7009 §2.1), and Looking Glass lists
  their `jti` values; revoking an access token leaves its refresh token
  valid. The authorization
  server metadata lists the accepted methods under
  `revocation_endpoint_auth_methods_supported`. After a `200`, introspection
  returns `active: false`. In Looking Glass, **Revoke as** selects the client
  that makes the request (`public-app`, `machine-client`, or the
  `private_key_jwt` client the page registered) and follows the client that
  obtained the captured token.
- Authorization code replay: a code presented a second time is refused with
  `invalid_grant`, and the tokens issued from it are revoked, including the
  access and refresh tokens obtained since by refreshing (RFC 6749 §4.1.2).
  The `Authorization Code Replayed: Tokens Revoked` event lists the revoked
  access token `jti` values.
- Device code: polling interval, `authorization_pending` vs `slow_down`
- private_key_jwt: assertion claims, signature algorithm/key binding, and the
  replay-protection event
- DPoP: proof claims (`htm`, `htu`, `iat`, `jti`), bound token's `cnf.jkt`,
  `token_type: DPoP`, and refresh-token binding surviving rotation
