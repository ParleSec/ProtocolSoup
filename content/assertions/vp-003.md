## What this requires

Section 5 lets Authorization Requests carry parameters beyond those it defines ("Additional request parameters, other than those defined in this section, MAY be defined and used, as described in [RFC6749]") and then says "The Wallet MUST ignore any unrecognized parameters, other than the transaction_data parameter." Ignoring cuts both ways. The wallet does not reject the request because an unknown parameter is present, and it does not let that parameter change what it does.

`transaction_data` is the one exception, and Section 5 spells it out: "Wallets that do not support this parameter MUST reject requests that contain it." The same ignore rule appears again for `direct_post` requests (Section 8.2) and for Verifier metadata (Section 11.1).

## Why it exists

Ignoring unknown parameters lets profiles and extensions add parameters without breaking wallets that do not implement them. The cost is that an ignored parameter has no effect, so a parameter whose meaning changes what the user consents to cannot be ignorable. That is why `transaction_data` is excluded: a wallet that dropped it would return a plain presentation to a verifier that asked for the user to authorise a specific transaction.

## What non-compliance looks like

A wallet that decodes request objects strictly and fails on any unknown claim rejects every request from a verifier using an extension. The other failure is a wallet that keeps acting on parameters OpenID4VP 1.0 does not define. A wallet that still honours the draft `client_id_scheme` parameter lets it override the Client Identifier Prefix in `client_id`, which is the confusion Section 14.8 warns about.

## How ProtocolSoup tests it

The hosted wallet (`backend/cmd/walletharness/main.go`) reads request-object claims by name and does not reject unknown claims. The removed draft `client_id_scheme` parameter is treated as unrecognised: `inferClientIDScheme` takes the request payload as an argument but never reads it, so only the prefix in `client_id` decides the trust model. The draft `presentation_definition` parameter gets the same treatment: the wallet has no Presentation Exchange support, so it neither matches credentials against that parameter nor sends `presentation_submission`, and credential selection follows `dcql_query` or the `scope` alias alone.

`TestInferClientIDSchemeUsesClientIDPrefixOnly` passes payloads whose `client_id_scheme` conflicts with the `client_id` and asserts that the classification follows the `client_id` every time: `x509_hash:thumbprint` stays `x509_hash`, and an `https` URL and a `did:web` identifier stay pre-registered. `TestResolveRequestContextIgnoresUnrecognizedParameters` resolves a signed request object that carries `presentation_definition`, `client_id_scheme` and an arbitrary `x-unrecognized` claim beside a valid `dcql_query`. It asserts that resolution succeeds and that the response URI, nonce and DCQL query are the ones the request defines. Neither test sends a full presentation, so the `direct_post` body is not checked.
