## What this requires

HAIP 1.0 Section 4 says that, when implementing OpenID4VCI, both the Wallet and the Credential Issuer "MUST comply with the provisions of [FAPI2_Security_Profile] that are applicable to this specification. This includes, but is not limited to using PKCE [RFC7636] with S256 as the code challenge method, Pushed Authorization Requests (PAR) [RFC9126] (where applicable) and the iss value in the Authorization response [RFC9207]." It narrows PAR: "Only required when using the Authorization Endpoint as defined in Section 5 of [OIDF.OID4VCI]."

For the wallet this means three things: send a `code_challenge` with `code_challenge_method=S256`, push the authorization request to the PAR endpoint, and reject an authorization response whose `iss` is missing or does not match the authorization server's issuer.

## Why it exists

HAIP does not give a reason in the text; each item closes a known authorization code flow attack. `plain` PKCE offers no protection if the authorization request leaks. PAR keeps request parameters off the front channel, where they could be read or altered. Without the `iss` check, a wallet talking to several authorization servers can be tricked into sending a code from one server to another (the mix-up attack RFC 9207 addresses).

## What non-compliance looks like

The wallet falls back to `code_challenge_method=plain`, or sends no challenge. It puts the full authorization request in the redirect URL when the server requires PAR. It accepts a callback with no `iss`, or with an `iss` for a different server, and goes on to redeem the code.

## How ProtocolSoup tests it

On the HAIP or PAR path, the hosted wallet's `buildPKCES256Pair` returns an S256 pair when the server advertises S256 or advertises nothing. Otherwise it fails with "authorization server does not advertise PKCE S256 and PAR/HAIP requires it", reported as `wallet_import_failed`. The wallet uses PAR when `require_pushed_authorization_requests` is true, or when a `pushed_authorization_request_endpoint` is advertised and the HAIP path applies. The PAR form always sets `code_challenge_method=S256`, and the follow-up redirect carries only `client_id` and `request_uri`. If the HAIP path applies but no PAR endpoint is advertised, the wallet sends a direct S256 authorization request. On the callback, `iss` is required on the HAIP path or when `authorization_response_iss_parameter_supported` is true. A missing or mismatched value ends the flow before the token request.

`TestPKCES256ChallengeGeneration` asserts that the challenge is the base64url SHA-256 of the verifier, and that the pair fails when only `plain` is advertised. `TestPARFormIncludesCodeChallengeMethodS256` checks a form map the test builds itself, so that part proves nothing about the PAR request the wallet sends. Its remaining assertion is that `buildPKCES256Pair` returns S256 when the metadata is silent. `TestRFC9207IssMismatchRejection` asserts that `validateAuthorizationResponseIss` rejects a mismatched `iss` and a missing required `iss`, and accepts a match. None of these tests drives the callback handler or checks other FAPI 2.0 provisions.
