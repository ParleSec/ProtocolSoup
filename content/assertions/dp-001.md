## What this requires

This is the first of the twelve checks RFC 9449 Section 4.3 lists after "To validate a DPoP proof, the receiving server MUST ensure the following". A request may carry zero or one `DPoP` header field. If it carries two or more, the server treats the proof as invalid and does not pick one of them to validate.

The check runs before anything else about the proof is looked at: the number of header fields decides the outcome, whatever their values.

## Why it exists

HTTP libraries disagree about duplicate header fields. Some hand the application the first value, some the last, and some join them with commas. When a proxy and the server behind it read different copies, the proof one of them checks is not the proof the other one acts on. Refusing the request whenever more than one field is present takes that ambiguity off the table, because there is no longer a choice to make.

## What non-compliance looks like

A server that reads the header with a "get first value" helper, such as Go's `http.Header.Get`, accepts a request with two `DPoP` fields and validates only the first. A second, unchecked proof then travels with the request, and any component that reads the last value sees a proof that was never verified.

At the token endpoint the correct response is an error per RFC 6749 Section 5.2 with `invalid_dpop_proof` as the value of the error parameter (RFC 9449 Section 5).

## How ProtocolSoup tests it

Every DPoP-protected endpoint reads the header through `dpop.ExtractHeader`, which takes all values of the field rather than the first. This covers the OAuth 2.0 token endpoint, the OAuth 2.0 protected resource, and the OID4VCI token and Credential endpoints. One value is returned trimmed; two or more are an error before any JWT parsing happens.

`TestExtractHeaderRejectsMultipleHeaderFields` passes two header values to `ExtractHeader` and asserts that it returns an error instead of either proof.
