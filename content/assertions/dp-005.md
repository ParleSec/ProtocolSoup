## What this requires

This is check 6 of RFC 9449 Section 4.3. The verification key is the public key carried in the proof's own `jwk` header, which Section 4.2 describes as "the public key chosen by the client". The server verifies the JWS signature over the header and payload with that key and rejects the proof if it does not verify.

The key is not looked up anywhere else: not by `kid`, not from a JWKS, and not from client registration.

## Why it exists

The signature is the "proof" in proof of possession. It shows that whoever sent the request holds the private key matching `jwk`, and that key's thumbprint is what an access token is bound to through `cnf.jkt` (Section 6). If the signature is not verified, a proof can be copied or edited freely and the binding means nothing.

## What non-compliance looks like

A server that decodes the JWT and reads its claims without verifying the signature accepts a proof with an edited `htu` or `iat`, or a proof whose `jwk` was swapped for someone else's public key. A server that verifies against some other key, such as a registered client key, checks possession of the wrong key.

At a token endpoint the correct response is HTTP 400 with `invalid_dpop_proof` (RFC 9449 Section 5).

## How ProtocolSoup tests it

`dpop.ValidateProof` parses the `jwk` header, rejects private material, validates the key and its fit with `alg`, converts it to a public key, and passes only that key to the JWT library's signature check. The proof's thumbprint is computed from the same key, so the value bound into `cnf.jkt` is the key the signature was checked with.

`TestValidateProofSucceedsForES256AndEdDSA` signs a valid proof with an ES256 key and with an Ed25519 key, and asserts that each validates and returns the expected `jti` and thumbprint. This is positive evidence only: it shows that a correctly signed proof is accepted, but no registry test presents a proof whose signature fails, such as one with an edited payload or one signed by a different key of the same type.
