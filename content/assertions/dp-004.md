## What this requires

This is check 5 of RFC 9449 Section 4.3. The `alg` header names an asymmetric digital signature algorithm registered with IANA, it is not `none`, and the server both implements it and is willing to accept it. Section 4.2 adds that `alg` "MUST NOT be none or an identifier for a symmetric algorithm (Message Authentication Code (MAC))".

All four conditions hold at once. An algorithm that is registered and asymmetric can still be refused because local policy does not allow it.

## Why it exists

Section 11.6 states it directly: "Implementers MUST ensure that only asymmetric digital signature algorithms (such as ES256) that are deemed secure can be used for signing DPoP proofs. In particular, the algorithm none MUST NOT be allowed." A proof with `alg` set to `none` carries no signature, so it proves nothing. A MAC algorithm needs a shared secret, and the only key a DPoP proof carries is the public `jwk` in its own header, so anyone who can read the proof could produce one.

## What non-compliance looks like

A verifier that trusts the header's `alg` and picks a verification routine from it accepts an unsigned proof when `alg` is `none`, or verifies an HS256 proof using key material taken from the proof itself. Either way, anyone can mint a proof for any key.

At a token endpoint the correct response is HTTP 400 with `invalid_dpop_proof` (RFC 9449 Section 5).

## How ProtocolSoup tests it

`dpop.ValidateProof` checks `alg` against a fixed allowlist of `RS256`, `ES256` and `EdDSA`, the same list both authorization servers publish as `dpop_signing_alg_values_supported`. Anything else is rejected before the key or signature is looked at. It then requires the `jwk` key type to fit the algorithm (RSA for `RS256`, EC P-256 for `ES256`, OKP Ed25519 for `EdDSA`), and the signature library is only handed the public key when its method matches the header `alg`.

`TestValidateProofRejectsAlgNone` builds an unsigned proof with `alg` set to `none` and a valid EC public `jwk`, and asserts that validation fails. `TestValidateProofRejectsSymmetricAlg` signs a proof with HS256 and a `jwk` of type `oct`, and asserts that validation fails. Both tests check only that an error is returned, not which check produced it.
