## What this requires

HAIP 1.0 Section 4.3 states: "Wallets MUST authenticate themselves at the PAR endpoint using the same rules as defined in Section 4.4 for client authentication at the token endpoint." Those rules sit in Section 4.4.1: "Wallets MUST use, and Issuers MUST require, an OAuth2 Client authentication mechanism at OAuth2 Endpoints that support client authentication (such as the PAR and Token Endpoints)."

A wallet that authenticates with a Wallet Attestation at the Token Endpoint does the same at the PAR endpoint, with the same `client_id`. It does not push an unauthenticated request and authenticate only later.

## Why it exists

HAIP does not give a reason in the text. The PAR endpoint is where the authorization server first decides which client it is dealing with, and it binds the stored request to that client. If PAR accepts weaker authentication than the token endpoint, an attacker can push requests under a wallet's `client_id` without holding its attestation. Using one rule set at both endpoints keeps the client identity behind `request_uri` the same as the one that later redeems the code.

## What non-compliance looks like

The PAR POST carries only a `client_id` form parameter, with no `OAuth-Client-Attestation` and `OAuth-Client-Attestation-PoP` headers, while the token request carries them. Or the two requests use different `client_id` values. An issuer that enforces HAIP answers the PAR request with an OAuth error and the flow stops there.

## How ProtocolSoup tests it

In the hosted wallet, `pushAuthorizationRequest` and the HAIP token exchange (`exchangeHAIPPreAuthorizedToken`, also used for `authorization_code` on the HAIP path) both call `buildClientAttestationHeaderPair` and post through `postHAIPFormWithDPoP`. Each request gets a Client Attestation JWT and a fresh PoP, with a challenge fetched when `challenge_endpoint` is advertised, plus a DPoP proof. Both use the attested `client_id`. `pushAuthorizationRequest` refuses to run without attestation material ("haip attestation material is not configured for PAR"). When PAR is chosen and attestation material is present, the wallet forces the HAIP path, so the token request is authenticated the same way.

None of the three registry tests compares the two endpoints. `TestPARFormIncludesCodeChallengeMethodS256` concerns PKCE, and its form check runs against a map the test builds itself. `TestBuildAuthorizationURLFromPAR` asserts that the redirect after PAR carries only `client_id` and `request_uri`. `TestShouldUseHAIPIssuancePathForExternalAttestedAS` asserts that an authorization server advertising `attest_jwt_client_auth` with required PAR and DPoP selects the attested path, and that `none` does not. The shared code path is what keeps the rules equal today; no test asserts it.
