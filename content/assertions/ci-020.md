## What this requires

HAIP 1.0 Section 6.1.1 mandates X.509 key resolution for SD-JWT VCs. "The SD-JWT VC MUST contain the credential issuer's signing certificate along with a trust chain in the x5c JOSE header parameter". "The X.509 certificate of the trust anchor MUST NOT be included", and the signing certificate "MUST NOT be self-signed." HAIP Section 4.1 applies the same `x5c` rule to signed Credential Issuer Metadata. That section cites "Section 11.2.3 in [OIDF.OID4VCI]", which is Section 12.2.3 in the OID4VCI 1.0 Final numbering and is the source of the 11.2 anchor above.

For status, HAIP Section 6.1 says "The status claim, if present, MUST contain status_list" and "Each Credential MUST have its own unique, unpredictable status list index, even when multiple Credentials reference the same status list URI". The Status List Token's signing key "MUST be included in the x5c JOSE header of the Token."

## Why it exists

Certificate-backed signing lets a Verifier resolve the issuer's key through a trust chain it already holds, rather than fetching a key from the issuer at presentation time. For status indices, HAIP points to the unlinkability considerations of the Status List specification. A shared or sequential index lets anyone who sees two Credentials tie them to one holder or one issuance.

## What non-compliance looks like

An issuer signs HAIP Credentials with a bare JWK and `kid`, or includes its self-signed root in `x5c`. An issuer allocates status indices sequentially, so neighbouring indices reveal issuance order. Or it advertises a URL `vct` that returns nothing, or returns Type Metadata with a different `vct`.

## How ProtocolSoup tests it

HAIP configurations set `UseX509CredentialSigner`. `issuance_drivers.go` then signs the issuer-signed JWT with ES256 using the document signer key and puts its certificate chain in `x5c`. It also adds `status.status_list` with an `idx` drawn from `crypto/rand` and checked for uniqueness, plus the list `uri`. Selectively disclosable claims such as `given_name` and `family_name` are top-level disclosures. `/oid4vci/status-lists/haip-sd-jwt-1` serves a `statuslist+jwt` signed the same way. With `Accept: application/jwt`, the metadata endpoint returns `openidvci-issuer-metadata+jwt` with `x5c`. The HAIP `vct` is the issuer's own `/oid4vci/credential-types/university-degree` URL, which serves matching Type Metadata.

`TestHAIPSDJWTCredentialUsesTrustedX5CSigner` asserts `alg` ES256, an `x5c` holding one leaf that is not a self-signed CA, and a chain that validates to the PKI's trust anchors. `TestSignedCredentialIssuerMetadataUsesTrustedX5CSigner` asserts `application/jwt`, the `typ`, `sub` and `credential_issuer` equal to the issuer, a chain that validates, and a signature that verifies under the leaf key. `TestHAIPStatusListAllocatesUniqueIndicesAndServesSignedToken` issues two Credentials and asserts different indices with the expected `uri`. It then fetches the list and asserts `typ` `statuslist+jwt`, `bits` 1 and a non-empty `lst`. `TestUniversityDegreeTypeMetadataMatchesAdvertisedVCT` fetches the `vct` URL and asserts the returned `vct` matches and `claims` is non-empty. No listed test checks the top-level claim model or the `x5c` header of the Status List Token.
