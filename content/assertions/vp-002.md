## What this requires

Section 5.9.2 gives the wallet two options when the text before the first colon is not a Client Identifier Prefix it recognises and supports: "the Wallet can treat the Client Identifier as referring to a pre-registered client or it may refuse the request." Either is conformant. If the wallet falls back, the whole value, colon included, is the pre-registered identifier it looks up.

The same section draws the consequence for pre-registration: "pre-registered clients MUST NOT contain a : character preceded immediately by a supported Client Identifier Prefix value in the first part of their Client Identifier." One prefix is not open to the fallback. Section 5.9.3 reserves `origin` for the Digital Credentials API and says "The Wallet MUST NOT accept this Client Identifier Prefix in requests."

## Why it exists

The set of prefixes is open: Section 5.9.3 says "Other specifications can define further Client Identifier Prefixes." A wallet will therefore meet prefixes it does not implement. Many ordinary identifiers also contain a colon, such as `https://verifier.example` or `did:web:verifier.example`. The fallback keeps those working as pre-registered clients, and refusal is the conservative choice for a wallet that wants no ambiguity.

## What non-compliance looks like

The faults lie outside the two permitted options. A wallet that guesses the meaning of an unknown prefix, for example by treating it like `redirect_uri`, applies trust rules the verifier never asked for. A wallet that strips the unknown prefix and looks up only the remainder breaks Section 14.8, which says "Wallets MUST always use the full Client Identifier, including the prefix if provided". A wallet that falls back to pre-registered for `origin:` accepts a prefix it MUST NOT accept.

## How ProtocolSoup tests it

The two ProtocolSoup components choose differently. The hosted wallet (`inferClientIDScheme` in `backend/cmd/walletharness/main.go`) refuses: any name, colon, rest value whose name is not one of the six defined prefixes is classified as unknown, and the request is rejected with `unsupported client_id scheme prefix`. That includes `origin:`. The exceptions are values starting with `http`, `https` or `did` followed by a colon, which it treats as pre-registered. `openid_federation` is recognised but not supported, and the wallet refuses it at signature verification with `client_id_scheme "openid_federation" is not yet supported by the wallet`.

The verifier's `ParseClientIDScheme` (`backend/internal/protocols/oid4vp/contracts.go`) takes the fallback and classifies an unrecognised prefix as `pre_registered`. Pre-registered is not in the verifier's supported set, so its create endpoint rejects such a `client_id` with `invalid_client`. `TestParseClientIDSchemeUsesFinalPrefixFallback` asserts the fallback: `origin:https://verifier.example`, `:example-client` and `redirect_uri :https://verifier.example` all parse as `pre_registered`. This test covers the verifier's parser, not the wallet. The wallet's refusal is asserted by the `invalid_scheme:attacker` case in `TestInferClientIDSchemeUsesClientIDPrefixOnly`, which is not linked to this requirement.
