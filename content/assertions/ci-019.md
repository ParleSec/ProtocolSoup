## What this requires

OID4VCI 1.0 Section 5.1.4 says "Use of Pushed Authorization Requests is RECOMMENDED". HAIP 1.0 makes the PAR endpoint an authenticated one. Section 4.3 says "Wallets MUST authenticate themselves at the PAR endpoint using the same rules as defined in Section 4.4 for client authentication at the token endpoint." Section 4.4.1 adds "if applicable, the client_id value in the PAR request MUST be the string in the sub value in the client attestation JWT." HAIP Section 4 brings in the FAPI 2.0 rules, "using PKCE [RFC7636] with S256 as the code challenge method", and requires DPoP support.

RFC 9126 defines the endpoint itself (Section 2) and the `request_uri` it returns (Section 4). The authorization server then uses that `request_uri`, not front-channel parameters, as the authorization request.

## Why it exists

OID4VCI Section 5.1.4 gives the reason: to "ensure confidentiality, integrity, and authenticity of the request data and to avoid issues caused by large requests sizes." Pushing the request over an authenticated back channel means the `authorization_details`, redirect URI and PKCE challenge the user later approves are the ones the attested Wallet sent. The browser cannot rewrite them.

## What non-compliance looks like

A PAR endpoint that accepts requests without client attestation lets any party register an authorization request under a Wallet's `client_id`. A `request_uri` that any client can redeem, or that lives for hours, can be replayed. An authorization endpoint that takes `redirect_uri` from the query instead of from the pushed request sends the code where an attacker chooses.

## How ProtocolSoup tests it

`handlePushedAuthorizationRequest` in `par.go` requires `application/x-www-form-urlencoded`. A missing or invalid attestation gets HTTP 401 `invalid_client`, and a `client_id` that differs from the attestation subject gets `invalid_request`. It also rejects a supplied `request_uri`, a `response_type` other than `code`, a non-HTTPS `redirect_uri`, and a missing S256 `code_challenge`, all with `invalid_request`. A DPoP proof is optional. If one is sent it is validated and its thumbprint must equal any `dpop_jkt`, and the thumbprint is stored. The handler returns HTTP 201 with a `urn:ietf:params:oauth:request_uri:` value and `expires_in` 90. At the authorization endpoint, `applyPushedAuthorizationRequest` loads the pushed request for the presenting `client_id` and replaces the query's `redirect_uri` and PKCE values with the stored ones. Authorization Server Metadata advertises `attest_jwt_client_auth` only when a trust anchor is configured.

`TestPushedAuthorizationRequestBindsAttestationDPoPAndCredentialDetails` pushes an attested, S256-bound request with `authorization_details`, once with a DPoP proof and once without. It asserts HTTP 201, the `request_uri` prefix, and a stored record for the `client_id`. The record must carry a DPoP thumbprint only when a proof was sent, and must keep the requested configuration. `TestAuthorizationServerMetadataAdvertisesAttestationWhenConfigured` sets `OID4VCI_CLIENT_ATTESTATION_TRUST_ANCHOR_PEM` and asserts that `attest_jwt_client_auth` is listed and that `client_attestation_signing_alg_values_supported` and `client_attestation_pop_signing_alg_values_supported` are both `["ES256"]`. Neither test sends a request without attestation or PKCE, checks the 90-second lifetime, or redeems the `request_uri` at the authorization endpoint.
