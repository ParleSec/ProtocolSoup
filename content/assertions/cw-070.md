## What this requires

Section 8.2 defines the two selectors of a Credential Request. `credential_identifier` is "REQUIRED when an Authorization Details of type openid_credential was returned from the Token Response. It MUST NOT be used otherwise." and "When this parameter is used, the credential_configuration_id MUST NOT be present." `credential_configuration_id` is "REQUIRED if a credential_identifiers parameter was not returned from the Token Response as part of the authorization_details parameter. It MUST NOT be used otherwise." and "When this parameter is used, the credential_identifier MUST NOT be present."

Every Credential Request carries exactly one of the two, and the Token Response decides which.

## Why it exists

The selectors answer the same question at different levels: a configuration names a type of Credential, an identifier names one authorised Credential Dataset. With both present the issuer has two answers that may disagree, and the result depends on which one its code reads first. With neither, the issuer cannot tell what is being asked for. Tying the choice to the Token Response keeps the request consistent with what the Authorization Server granted.

## What non-compliance looks like

A wallet that always sends `credential_configuration_id` and adds `credential_identifier` when it has one, producing a body with both. Or a wallet that ignores returned identifiers and sends only the configuration. Either is a malformed request, which Section 8.3.1.2 answers with `invalid_credential_request`.

## How ProtocolSoup tests it

`buildCredentialRequestBody` makes the choice in one place. If `credentialIdentifiersFromTokenResponse` found any `credential_identifiers` in the Token Response's `authorization_details`, the body gets `credential_identifier` and no `credential_configuration_id`. Otherwise it gets `credential_configuration_id`. With neither available it returns an error instead of sending a request. The extraction reads `credential_identifiers` without checking that the entry's `type` is `openid_credential`.

`TestCredentialRequestBuilderIdentifierExclusivity` gives `buildCredentialRequestBody` both a configuration identifier and an identifier list, and asserts that the body contains `credential_identifier` and not `credential_configuration_id`. It also asserts that `validateCredentialRequestSelectorExclusivity` rejects both values set together; that helper is not called on the request path, so this part of the test does not exercise the wallet's behaviour. The configuration-only case and the case with neither selector are not asserted.
