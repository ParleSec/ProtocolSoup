## What this requires

This requirement states how ProtocolSoup's verifier applies several OpenID4VP rules; the sentence itself is not spec text. "Redirect response modes" here means `direct_post` and `direct_post.jwt` responses to requests the wallet received by redirect or QR code, as opposed to the Digital Credentials API. For those, the response must carry the `state` the verifier put in the Authorization Request, and the value must match exactly. Section 5.3 makes this a MUST whenever a presentation without Holder Binding is requested: the Verifier MUST "check that the same state value is returned in the Authorization Response". ProtocolSoup applies it to every redirect-invoked request.

With `direct_post.jwt` the wallet posts only an encrypted `response`, so `state` sits inside the JWE. Section 8.3 gives the verifier a way to find the right key first: "If the selected public key contains a kid parameter, the JWE MUST include the same value in the kid JWE Header Parameter (as defined in Section 4.1.6) of the encrypted response. This enables the Verifier to easily identify the specific public key that was used to encrypt the response." After decryption, the inner `state` must equal the issued one.

## Why it exists

A `direct_post` response reaches the Response URI from the wallet, not from the browser that started the flow, so the verifier needs a value that ties the response to a request. Section 14.3.2 says "The Verifier SHOULD protect its Response URI from inadvertent requests by checking that the value of the received state parameter corresponds to a recent Authorization Request." `state` is the value the wallet read from the signed request and sends back. If a second identifier, such as an internal `request_id`, could stand in for it, the verifier would accept responses that never carried the value the wallet received, and the check would be skipped.

## What non-compliance looks like

A verifier looks up the session by an identifier from its own URLs and skips the `state` comparison when that lookup succeeds. A verifier compares `state` loosely, by prefix or ignoring case. A verifier selects a session for an encrypted response, decrypts it, and accepts the result without comparing the decrypted `state` to the session's.

## How ProtocolSoup tests it

`handleWalletResponse` (`backend/internal/protocols/oid4vp/handlers.go`) rejects any response to a redirect-invoked request whose `state` is empty or not byte-equal to the issued value, with 400 `invalid_request` and `state must exactly match the authorization request`, even when a valid `request_id` is supplied. When an encrypted response arrives with neither `state` nor `request_id`, `requestSessionForEncryptedResponse` reads the `kid` from the JWE protected header and selects the single unexpired session whose ephemeral ECDH-ES key has that `kid`. The code does not rely only on the `kid`. If the `kid` is absent or matches no session, it tries to decrypt against each active session key and accepts the single session whose decrypted `state` equals its own. Whichever way the session is found, the decrypted `state` is then compared exactly, and a mismatch fails with `state mismatch in encrypted response payload`.

`TestRedirectWalletResponseRequiresExactStateEvenWithRequestID` posts a `request_id` and a `vp_token` with no `state` to `/oid4vp/response` for a `direct_post` request, and asserts 400 with `invalid_request`. It does not check the error description and does not try a wrong but non-empty `state`. `TestHAIPDirectPostJWTSDJWTProvisionsECDHESEncryption` creates a HAIP `direct_post.jwt` SD-JWT VC request and asserts that an ECDH-ES response key was provisioned, that A128GCM and A256GCM are advertised, and that a JWE-shaped value whose header carries that key's `kid` selects that session. It also asserts the request object's `aud` is `https://self-issued.me/v2`. Neither test covers the decrypted-state comparison or the fallback used when the `kid` is missing.
