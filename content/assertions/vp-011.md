## What this requires

Section 8.4 says "If the Wallet does not support transaction_data parameter, it MUST return an error upon receiving a request that includes it." Section 5 repeats the rule as the exception to ignoring unknown parameters: "Wallets that do not support this parameter MUST reject requests that contain it." Section 5.1 extends it to wallets that do support the parameter: "The Wallet MUST return an error if a request contains even one unrecognized transaction data type or transaction data not conforming to the respective type definition."

Section 8.5 defines the error code. `invalid_transaction_data` applies when, among other cases, an object in the `transaction_data` structure "contains an unknown or unsupported transaction data type value".

## Why it exists

Section 8.4 describes what the parameter is for: "The transaction data mechanism enables a binding between the user's identification/authentication and the user’s authorization, for example to complete a payment transaction, or to sign specific document(s) using QES (Qualified Electronic Signatures)." It also says "The Wallet that received the transaction_data parameter in the request MUST include a representation or reference to the data in the respective Credential presentation."

A wallet that silently drops the parameter returns an ordinary presentation. The user was never shown the transaction, and the presentation is not bound to it. A verifier that does not check for the binding could then treat proof of identity as authorisation of a payment or signature the user never saw.

## What non-compliance looks like

The wallet treats `transaction_data` like any other unknown parameter: it shows the normal consent screen, presents the credential, and posts a `vp_token` with no transaction binding to the Response URI. Nothing on the wire signals that the transaction was ignored.

## How ProtocolSoup tests it

The hosted wallet implements no transaction data type. After decoding a request object and checking its `typ`, `resolveRequestEnvelope` (`backend/cmd/walletharness/main.go`) calls `rejectUnsupportedTransactionData`, which refuses every request object carrying `transaction_data`. A malformed value (not a non-empty array, an entry that is not a base64url string, not a JSON object, or without a `type`) gets a description of the defect. A well-formed entry fails with `transaction data type "..." is not supported`. Every resolve, preview, present and submit API returns HTTP 400 with `"error": "invalid_transaction_data"` and that description. The error goes back to the caller of the wallet's API, which is the wallet UI or Looking Glass. The wallet does not send an Authorization Error Response to the verifier's Response URI.

`TestPresentationAPIsRejectUnsupportedTransactionData` builds request objects with `typ` `oauth-authz-req+jwt` that carry either a well-formed entry of type `https://example.com/transaction` or the malformed value `%%%`. It posts each one to the resolve, preview, present and submit handlers, and asserts a 400 status, `invalid_transaction_data`, and the expected text in `error_description` for every combination. It proves that no wallet entry point presents with an unsupported `transaction_data`. It does not cover delivery of the error to the verifier.
