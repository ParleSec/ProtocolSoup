## What this requires

Section 6.2 defines `credential_identifiers` inside an `openid_credential` entry of the Token Response's `authorization_details` as "A non-empty array of strings, each uniquely identifying a Credential Dataset that can be issued using the Access Token returned in this response." It then states: "The Wallet MUST use these identifiers together with an Access Token in subsequent Credential Requests."

Once the Authorization Server has returned identifiers, the wallet asks for Credentials by `credential_identifier` and presents the Access Token from the same response. Section 8.2 is the other side of this: with an identifier in the request, `credential_configuration_id` is not sent.

## Why it exists

A Credential Configuration describes a type of Credential; a Credential Dataset is the specific data to be issued, such as one of two diplomas a user holds. The identifiers are how the Authorization Server tells the Credential Issuer which datasets the user authorised. A wallet that falls back to the configuration identifier leaves the issuer to guess which dataset is meant, or to issue something the user did not choose.

## What non-compliance looks like

The Token Response includes `"credential_identifiers": ["CivilEngineeringDegree-2023"]`, and the wallet's Credential Request still carries `credential_configuration_id`. The issuer rejects the request, or issues a dataset other than the one authorised. The error code for that rejection is `invalid_credential_request` from Section 8.3.1.2, which covers a request that "is missing a required parameter, includes an unsupported parameter or parameter value".

## How ProtocolSoup tests it

`credentialIdentifiersFromTokenResponse` collects `credential_identifiers` from every entry in the Token Response's `authorization_details` and removes duplicates. `buildCredentialRequestBody` then sends the first of them as `credential_identifier` and leaves `credential_configuration_id` out. The request goes to the Credential Endpoint with the Access Token from that Token Response. If several identifiers are returned, the wallet requests only the first; the other datasets are not requested.

`TestCredentialRequestBuilderIdentifierExclusivity` passes both a configuration identifier and `credential_identifiers: ["id-1"]` to `buildCredentialRequestBody`. It asserts that the body has `credential_identifier` set to `id-1` and no `credential_configuration_id`. It also asserts that the separate `validateCredentialRequestSelectorExclusivity` helper rejects both selectors together. The test starts from identifiers already extracted, so it does not cover parsing a Token Response or the Access Token on the request.
