## What this requires

This is check 7 of RFC 9449 Section 4.3. The `jwk` header must be a public key only. Section 4.2 says of `jwk`: "It MUST NOT contain a private key." If any private key member is present, the server rejects the proof rather than ignoring the extra members and carrying on with the public part.

## Why it exists

A client that puts its private key in the header has given that key to every party that sees the proof: proxies, logs, and the server itself. From then on anyone holding a copy of the proof can mint new proofs for the same key, so possession proves nothing. Accepting such a proof also means the server receives and may store or log private key material it should never have.

## What non-compliance looks like

A server that strips `d` from the header and verifies with what remains accepts a proof that would validate under the public members alone, because the public half still matches the signature. The client keeps working and the leak goes unnoticed.

At a token endpoint the correct response is HTTP 400 with `invalid_dpop_proof` (RFC 9449 Section 5).

## How ProtocolSoup tests it

`dpop.ValidateProof` parses the `jwk` header and rejects it if any of `d`, `p`, `q`, `dp`, `dq`, `qi`, `oth` or `k` is present, before any signature check. There is no strip-and-continue path.

`TestValidateProofRejectsPrivateKeyInJWKHeader` signs an otherwise valid ES256 proof whose `jwk` header has a `d` member added, and asserts that validation returns an error. Only the `d` member is exercised by this test.
