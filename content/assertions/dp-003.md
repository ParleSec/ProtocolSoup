## What this requires

This is check 4 of RFC 9449 Section 4.3. The JOSE header of the proof carries `typ` with the value `dpop+jwt`. A proof with no `typ`, or with a generic value such as `JWT`, is not a DPoP proof and is rejected.

Section 4.2 describes the parameter as "A field with the value dpop+jwt, which explicitly types the DPoP proof JWT as recommended in Section 3.11 of [RFC8725]".

## Why it exists

RFC 9449 states the reason in Section 11.5: "Servers accepting signed DPoP proof JWTs MUST verify that the typ field is dpop+jwt in the headers of the JWTs to ensure that adversaries cannot use JWTs created for other purposes." Without explicit typing, any JWT a client signs with the same key, such as a client assertion or a credential key proof, could be presented as a DPoP proof if its claims happen to line up.

## What non-compliance looks like

A server that never reads `typ` accepts a signed JWT built for another protocol step as long as the signature verifies with the embedded `jwk` and the claims it does check are present. The proof then demonstrates nothing about the request it travels with.

At a token endpoint the correct response is HTTP 400 with `invalid_dpop_proof` (RFC 9449 Section 5).

## How ProtocolSoup tests it

`dpop.ValidateProof` decodes the header and compares `typ` with the constant `dpop+jwt` as an exact string before it looks at `alg`, `jwk` or the signature. Any other value, including a missing `typ`, fails validation.

`TestValidateProofRejectsWrongTyp` signs an otherwise valid ES256 proof with `typ` set to `JWT` and asserts that validation returns an error.
