## What this requires

HAIP 1.0 Section 4.5.1 opens with "Wallets MUST support key attestations." With the OpenID4VCI Appendix D format, the wallet signs a `key-attestation+jwt` that lists the holder keys in `attested_keys`. The proofs in the Credential Request carry it, for example in the `key_attestation` header of a `jwt` proof.

The second sentence of this requirement is not HAIP text. Its basis is OpenID4VCI 1.0 Appendix D.2, which defines the `key_storage` and `user_authentication` values, for example "iso_18045_moderate: It MUST be used when key storage or user authentication is resistant to attack with attack potential "Moderate", equivalent to VAN.4 according to [ISO.18045]." A wallet whose keys live in ordinary process memory or on disk has no basis for asserting such a level.

## Why it exists

A key attestation is how an Issuer learns that a holder key is protected the way its policy demands before it binds a credential to that key. The attestation is only worth something if its claims are true. A software wallet that claims `iso_18045_moderate` passes an Issuer's `key_attestations_required` check that exists to exclude it, and the credential ends up bound to a key with weaker protection than the Issuer accepted.

## What non-compliance looks like

The wallet sends a bare `jwt` proof to a configuration whose metadata contains `key_attestations_required`, and the Issuer rejects it. Or the wallet hard-codes `"key_storage":["iso_18045_moderate"]` so it always meets the Issuer's threshold, whatever key storage it actually uses.

## How ProtocolSoup tests it

On the HAIP path, the hosted wallet builds one ES256 key attestation for all holder keys in the request. It carries `attested_keys`, `iat` and the `c_nonce` as `nonce`, and is signed with the key from `WALLET_CLIENT_ATTESTATION_KEY_ATTESTATION_JWK_JSON`. Each `openid4vci-proof+jwt` carries it in the `key_attestation` header. The wallet takes this path when a configuration's `proof_types_supported.jwt` contains `key_attestations_required`. The attestation never carries `key_storage` or `user_authentication`. OpenID4VCI 1.0 Appendix D.2 defines each value as an assertion of attack resistance; for example, `iso_18045_basic` "MUST be used when key storage or user authentication is resistant to attack with attack potential "Basic", equivalent to VAN.2". The hosted wallet holds software keys that have had no ISO/IEC 18045 vulnerability analysis, so there is no level it can back, and no setting makes it claim one. When a configuration's `key_attestations_required` names `key_storage` or `user_authentication` values, `refuseUnbackedKeyAttestationLevels` stops issuance before the Token Request with a 400 that names the demanded levels.

`TestHAIPBatchProofsShareSingleKeyAttestation` builds the key attestation for a batch request and asserts it carries neither `key_storage` nor `user_authentication`. `TestRefuseUnbackedKeyAttestationLevels` asserts that an empty `key_attestations_required` is accepted and that a demand for a `key_storage` or `user_authentication` level is refused with a 400 naming it. `TestConfigurationRequiresKeyAttestationFromMetadata` asserts that `key_attestations_required` selects the attested path and that its absence does not. ProtocolSoup's own HAIP mDL configuration asks for no level: it publishes `key_attestations_required` as an empty object, which OpenID4VCI 1.0 Section 12.2.4 describes as "indicating a key attestation is needed without additional constraints".
