## What this requires

HAIP 1.0 Section 4.5.1 opens with "Wallets MUST support key attestations." With the OpenID4VCI Appendix D format, the wallet signs a `key-attestation+jwt` that lists the holder keys in `attested_keys`. The proofs in the Credential Request carry it, for example in the `key_attestation` header of a `jwt` proof.

The second sentence of this requirement is not HAIP text. Its basis is OpenID4VCI 1.0 Appendix D.2, which defines the `key_storage` and `user_authentication` values, for example "iso_18045_moderate: It MUST be used when key storage or user authentication is resistant to attack with attack potential "Moderate", equivalent to VAN.4 according to [ISO.18045]." A wallet whose keys live in ordinary process memory or on disk has no basis for asserting such a level.

## Why it exists

A key attestation is how an Issuer learns that a holder key is protected the way its policy demands before it binds a credential to that key. The attestation is only worth something if its claims are true. A software wallet that claims `iso_18045_moderate` passes an Issuer's `key_attestations_required` check that exists to exclude it, and the credential ends up bound to a key with weaker protection than the Issuer accepted.

## What non-compliance looks like

The wallet sends a bare `jwt` proof to a configuration whose metadata contains `key_attestations_required`, and the Issuer rejects it. Or the wallet hard-codes `"key_storage":["iso_18045_moderate"]` so it always meets the Issuer's threshold, whatever key storage it actually uses.

## How ProtocolSoup tests it

On the HAIP path, the hosted wallet builds one ES256 key attestation for all holder keys in the request. It carries `attested_keys`, `iat` and the `c_nonce` as `nonce`, and is signed with the key from `WALLET_CLIENT_ATTESTATION_KEY_ATTESTATION_JWK_JSON`. Each `openid4vci-proof+jwt` carries it in the `key_attestation` header. The wallet takes this path when a configuration's `proof_types_supported.jwt` contains `key_attestations_required`. `key_storage` and `user_authentication` are added only when `WALLET_KEY_ATTESTATION_KEY_STORAGE` or `WALLET_KEY_ATTESTATION_USER_AUTHENTICATION` is set. The wallet does not compare them with the Issuer's demands, so an unmet level is the Issuer's HTTP 400.

`TestIso18045ModerateNotClaimedWhenEnvUnset` asserts that no levels are produced when both variables are empty, and that `iso_18045_moderate` is passed through when set. `TestConfigurationRequiresKeyAttestationFromMetadata` asserts that `key_attestations_required` selects the attested path and that its absence does not. The tests show the wallet claims nothing by default. Whether a deployment that sets these variables is telling the truth about its key storage is outside what any test can check. ProtocolSoup's own HAIP mDL configuration no longer asks for a level: it publishes `key_attestations_required` as an empty object, which OpenID4VCI 1.0 Section 12.2.4 describes as "indicating a key attestation is needed without additional constraints". The hosted wallet therefore needs no level claim, and the hosted deployment sets neither variable.
