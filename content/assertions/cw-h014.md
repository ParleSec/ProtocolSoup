## What this requires

HAIP 1.0 Section 4.5.1 opens with "Wallets MUST support key attestations." With the OpenID4VCI Appendix D format, the wallet signs a `key-attestation+jwt` that lists the holder keys in `attested_keys`, and the proofs in the Credential Request carry it, for example in the `key_attestation` header of a `jwt` proof.

The same section fixes how that JWT names its signing key. "The public key used to validate the signature on the key attestation MUST be included in the x5c JOSE header of the key attestation", so the first certificate in `x5c` holds the key that verifies the signature. "The X.509 certificate of the trust anchor MUST NOT be included in the x5c JOSE header of the key attestation", so the chain stops short of the root the Issuer already holds. And "The X.509 certificate signing the key attestation MUST NOT be self-signed": the signing certificate must itself be issued by something the Issuer can trace to its anchor.

## Why it exists

A key attestation is how an Issuer learns that a holder key is protected the way its policy demands before it binds a credential to that key. The attestation is only worth something if the Issuer can tell who signed it. Putting the signing certificate in `x5c` lets the Issuer verify the signature and walk the chain to an anchor it already trusts; leaving the anchor out keeps the wallet from nominating its own root, because a root that travels with the message proves nothing. A self-signed signing certificate would be exactly that: a key vouching for itself.

## What non-compliance looks like

The wallet sends a bare `jwt` proof to a configuration whose metadata contains `key_attestations_required`, and the Issuer rejects it. Or the key attestation's `x5c` carries the ecosystem root certificate as its last entry, or a single self-signed certificate minted by the wallet, so the Issuer either refuses the chain or, worse, accepts a root the wallet chose.

## How ProtocolSoup tests it

On the HAIP path, the hosted wallet builds one ES256 key attestation for all holder keys in the request. It carries `attested_keys`, `iat` and the `c_nonce` as `nonce`, and is signed with the key from `WALLET_CLIENT_ATTESTATION_KEY_ATTESTATION_JWK_JSON`, whose `x5c` becomes the attestation's `x5c` header. Each `openid4vci-proof+jwt` carries it in the `key_attestation` header. The wallet takes this path when a configuration's `proof_types_supported.jwt` contains `key_attestations_required`.

The wallet refuses to start with attestation material that breaks the x5c rules: `validateAttestationX5C` requires the first certificate to carry the signing key, every certificate to be signed by the next, and no certificate to be self-signed, which is what a trust anchor in the chain would be. `TestValidateAttestationX5CExcludesTheTrustAnchor` accepts a leaf-only chain and refuses one that carries its self-signed root or a leaf for another key. `TestHAIPBatchProofsShareSingleKeyAttestation` builds the key attestation for a batch request and asserts every proof carries the same one. `TestConfigurationRequiresKeyAttestationFromMetadata` asserts that `key_attestations_required` selects the attested path and that its absence does not. The captured passing exchange reads the key attestation the production wallet sent and checks its signature verifies under the first `x5c` certificate and that the chain holds no self-signed certificate.
