## What this requires

HAIP 1.0 Section 4 profiles the FAPI 2.0 sender-constrained token requirement: "Sender-constrained access token: MUST support DPoP as defined in [RFC9449]. Note that this requires Wallets to be prepared to handle the DPoP-Nonce HTTP response header from the Credential Issuer's Nonce Endpoint, as well as from other applicable endpoints of the Credential Issuer and Authorization Server." The keyword binds DPoP support; nonce handling is stated as what that support entails.

OpenID4VCI 1.0 Section 7.2 describes the Nonce Endpoint case: "The Credential Issuer MAY provide a DPoP nonce in an HTTP header as defined in Section 8.2 of [RFC9449]. In this case, the Wallet uses the new nonce value in the DPoP proof when presenting an access token at the Credential Endpoint."

## Why it exists

The HAIP text gives the reason for the note: servers may hand out a DPoP nonce from any of these endpoints, so a wallet that only knows how to sign a proof without a nonce cannot finish the flow. A server-supplied nonce lets the server limit the lifetime of DPoP proofs, so proofs generated in advance cannot be used later (RFC 9449 Sections 8 and 11.2). A wallet that ignores them is stuck on the first `use_dpop_nonce` error.

## What non-compliance looks like

The wallet sends a bearer token where the issuer expects DPoP. Or it receives HTTP 400 with `"error":"use_dpop_nonce"`, or HTTP 401 with `WWW-Authenticate: DPoP error="use_dpop_nonce"`, and gives up instead of retrying with the `DPoP-Nonce` value in the proof's `nonce` claim.

## How ProtocolSoup tests it

On the HAIP path the hosted wallet creates a P-256 DPoP key per issuance session. It sends `dpop_jkt` in PAR and signs ES256 `dpop+jwt` proofs (`jti`, `htm`, `htu`, `iat`, plus `ath` when presenting the access token) at the PAR, token, Credential and deferred endpoints, and at the notification endpoint when the token type is `DPoP`. `doDPoPJSONRequest` and the notification sender treat HTTP 400 or 401 carrying `use_dpop_nonce`, or a 401 with only `DPoP-Nonce`, as a nonce challenge. They retry once with that value as the proof `nonce`, or fail with "use_dpop_nonce without DPoP-Nonce header". On a retry the wallet also mints a fresh client attestation PoP. The Nonce Endpoint request is sent without a DPoP proof, and any `DPoP-Nonce` header on its response is not read. The Credential Endpoint nonce is therefore picked up only from a challenge.

`TestDoDPoPJSONRequestRefreshesClientAttestationPoPOnNonceRetry` runs an authorization server style 400 JSON challenge and a resource server style 401 `WWW-Authenticate` challenge. Each subtest asserts exactly two attempts, a `DPoP` header on the retry, a new PoP `jti`, and the success payload. It does not decode the retry proof to check its `nonce` claim. `TestNotifyCredentialAcceptedUsesNotificationBinding` uses a `Bearer` token and asserts the `Authorization` header and notification body, so it does not exercise DPoP.
