## What this requires

This row is ProtocolSoup's statement of how it meets RFC 9449 Section 8, not a sentence quoted from the RFC. Section 8 says the server-provided nonce mechanism "can be used to limit the lifetime of DPoP proofs" and that "Nonce values MUST be unpredictable." The row turns those into two properties: a nonce stops being accepted once its lifetime has passed, and if the server cannot read random bytes it reports an error instead of issuing a fallback value.

The RFC leaves when to issue a new nonce to the server; Section 8 calls that logic "out of scope of this document".

## Why it exists

A nonce that never expires does not limit anything: a proof pre-generated with it works as long as the nonce does, which is the attack Section 11.2 describes. A predictable nonce fails in the same way, because the attacker can sign proofs for future nonce values ahead of time. Falling back to a counter, a timestamp or an empty string when the random source fails would hand out exactly such values.

## What non-compliance looks like

A server that issues one nonce at start-up and accepts it forever, or that keeps every nonce it ever issued as valid, gives pre-generated proofs an unlimited life. A server that ignores the error from its random source and issues zeroed or empty bytes gives every client the same guessable nonce.

## How ProtocolSoup tests it

Each enabled nonce space uses a `NonceIssuer` with a five-minute lifetime that keeps at most two values, the current one and the one before it. Rotation happens on the next `Issue` or `Valid` call after the lifetime has passed. The old value is kept as the previous one only if less than two lifetimes have passed since it was issued; otherwise it is dropped. So a value can be accepted for somewhat longer than one lifetime, but never once it has fallen out of both slots. Nonces are 24 bytes from `crypto/rand`, base64url-encoded. A read failure is returned as an error, and the endpoints answer HTTP 500 with `server_error` rather than issuing a nonce.

`TestNonceIssuerRejectsOldNonceAfterLongIdlePeriod` issues a nonce with a 10 ms lifetime, waits 25 ms, and asserts that the old value is no longer valid. `TestNonceIssuerFailsClosedWhenEntropyUnavailable` replaces the random source with one that always fails and asserts that `Issue` returns an error and an empty nonce.
