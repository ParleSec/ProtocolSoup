## What this requires

RFC 9449 Section 8 lets an authorization server supply a nonce in a `DPoP-Nonce` response header, and this sentence binds the server for every proof that follows. Two words in it do the work. The match has to be "exactly" a supplied value, so nothing looser than equality will do. And the value has to have been supplied "recently", so a nonce does not stay acceptable for ever: once the server has moved on from it, a proof that carries it is refused like any other mismatch.

The RFC sets no lifetime. Section 8 gives the intent, "clients need to keep only one nonce value and servers need to keep a window of recent nonces", and Section 8.2 leaves the timing to the server: "It is up to the authorization server when to supply a new nonce value for the client to use."

The refusal can carry the way to recover. Section 8 says "The rejection response MAY include a DPoP-Nonce HTTP header providing a new nonce value to use for subsequent requests", and that the `use_dpop_nonce` error code "is used when supplying a new nonce value when there was a nonce mismatch". Section 9 has resource servers provide nonces "in the same way that authorization servers do as described in Sections 8 and 8.2".

## Why it exists

Section 8 states what the mechanism is for: it "can be used to limit the lifetime of DPoP proofs", because without it "a malicious party controlling the client (potentially including the end-user) can create DPoP proofs for use arbitrarily far in the future." A nonce limits a proof's lifetime only if the nonce itself stops being accepted. Section 11.2 says so directly: "By providing new nonce values at times of its choosing, the server can limit the lifetime of DPoP proofs, preventing pre-generated DPoP proofs from being used."

## What non-compliance looks like

A server that accepts every nonce it has ever supplied, or that supplies one at start-up and never replaces it, lets a proof signed over an old nonce work indefinitely, which gives pre-generated proofs the unlimited life Section 11.2 describes. A server that compares loosely, by prefix or without regard to case, accepts values it never supplied.

## How ProtocolSoup tests it

Where nonces are required, each nonce space is a `NonceIssuer` with a five-minute lifetime that keeps at most two values, the current one and the one before it. Rotation happens on the next `Issue` or `Valid` call after the lifetime has passed. The old value is kept as the previous one only if less than two lifetimes have passed since it became current; otherwise it is dropped. A value is therefore accepted for at least five minutes after the server hands it out and for less than fifteen minutes in all, and never once it has left both slots. `Valid` compares the proof's `nonce` claim with the two values in constant time. Any other value, or none, gets `use_dpop_nonce` with a new `DPoP-Nonce` header: HTTP 400 at the OAuth 2.0 and OID4VCI token endpoints, and HTTP 401 with a `WWW-Authenticate: DPoP` challenge at the resource endpoints, which keep a nonce space of their own.

`TestNonceIssuerRejectsOldNonceAfterLongIdlePeriod` issues a nonce with a 10 ms lifetime, waits 25 ms, and asserts that the old value is no longer valid. `TestNonceIssuerRejectsUnknownNonce` asserts that a value the issuer never issued, and an empty one, are not valid. `TestTokenEndpointForeignOrStaleNonceIsRejectedAsFreshChallenge` sends the OAuth 2.0 token endpoint a proof whose `nonce` the endpoint never supplied and asserts HTTP 400 `use_dpop_nonce` with a `DPoP-Nonce` header.

The captured failing exchange sends the supplied nonce with its last character replaced and then with its last character removed. A nonce the server has dropped is not captured, because the server keeps a supplied nonce for at least five minutes, longer than a capture run waits; the first test above covers that case with a shortened lifetime.
