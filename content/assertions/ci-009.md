## What this requires

OID4VCI 1.0 Section 7 states this requirement. If the issuer expects a `c_nonce` in key proofs, it has to provide the endpoint that hands those values out and advertise it in Credential Issuer Metadata. Section 12.2.4 defines `nonce_endpoint` and says "If omitted, the Credential Issuer does not require the use of c_nonce." Section 8.2 names the source: "The c_nonce value is retrieved from the Nonce Endpoint as defined in Section 7."

## Why it exists

In OID4VCI 1.0 Final the Nonce Endpoint is the only defined way to obtain a `c_nonce`; the Token Response no longer carries one. An issuer that required a nonce without offering the endpoint would reject every proof, and a Wallet reading the metadata would conclude from the missing `nonce_endpoint` that no nonce was needed. Section 13.8 also states that it "is RECOMMENDED that Credential Issuers utilize the Nonce Endpoint" to protect against proof replay.

## What non-compliance looks like

The issuer's metadata has no `nonce_endpoint`. The Wallet sends a proof JWT with no `nonce` claim and gets `invalid_proof`, which Section 8.3.1.2 uses when "at least one of the key proofs does not contain a c_nonce value". A Wallet built for older drafts may also wait for `c_nonce` in the Token Response, which a Final issuer does not send.

## How ProtocolSoup tests it

ProtocolSoup requires a nonce in every proof: `validateProofJWT` returns "proof nonce is required", which the Credential Endpoint reports as `invalid_proof`. To match, it serves `POST /oid4vci/nonce` and always publishes `nonce_endpoint` as the issuer identifier plus `/nonce`. `handleCredentialIssuerMetadata` would return `server_error` if that URL were empty, but the URL is built from the issuer identifier, so in practice that guard cannot fail.

`TestCredentialIssuerMetadataWellKnown` fetches `/.well-known/openid-credential-issuer` and asserts that `nonce_endpoint` is a non-empty string. It also checks `credential_issuer`, `credential_endpoint`, `notification_endpoint`, `batch_credential_issuance.batch_size`, the absence of the draft `token_endpoint` and `batch_credential_endpoint` members, and that `authorization_servers` matches the RFC 8414 metadata issuer. This is indirect evidence. It shows the endpoint is advertised, but it does not call the advertised URL and does not show that proofs without a nonce are rejected. The Nonce Endpoint itself is exercised under CI-012.
