## What this requires

OID4VCI 1.0 Section 7.1 says "The Nonce Endpoint is not a protected resource, meaning the Wallet does not need to supply an access token to access it." Section 7.2 sets the rules for the value and the response: `c_nonce` is REQUIRED, "New challenge values MUST be unpredictable", and "the Credential Issuer MUST make the response uncacheable by adding a Cache-Control header field including the value no-store."

The registry statement adds "MUST" to the access token rule. The wording in Section 7.1 itself is the descriptive sentence quoted above.

## Why it exists

The specification does not give a reason for leaving the endpoint unprotected. The concrete effect is that a Wallet can obtain a nonce with one plain POST. An issuer that put the endpoint behind token checks would reject Wallets that follow Section 7.1 and send no token. With DPoP-bound tokens, it would also add DPoP proof and nonce handling to a step that only exists to hand out a challenge.

## What non-compliance looks like

The issuer returns HTTP 401 `invalid_token` to a nonce request that has no `Authorization` header. Or the issuer runs the request through its resource-server middleware, so a stale or duplicated DPoP header breaks nonce acquisition. On the value side, an issuer that returns counters or timestamps as nonces, or lets the response be cached, fails Section 7.2.

## How ProtocolSoup tests it

`handleNonce` in `handlers.go` does not call the access-token or DPoP checks used by the Credential, Deferred Credential and Notification endpoints. It draws a 24-character value from `crypto/rand`, records it with a five-minute expiry, emits a "Credential Nonce Issued" Looking Glass event, and returns HTTP 200 JSON with `Cache-Control: no-store`. The body also carries `c_nonce_expires_in`, which Section 7.2 does not define.

`TestNonceEndpointIsPublicWithIrrelevantAuthHeaders` obtains a DPoP-bound access token, then POSTs to `/oid4vci/nonce` with `Authorization: DPoP` and two `DPoP` header fields. A protected endpoint would reject that request under RFC 9449 Section 4.3. The test asserts HTTP 200 and a non-empty `c_nonce`. It does not send a request with no headers at all, and it does not check that two calls return different values or that `Cache-Control` is set.
