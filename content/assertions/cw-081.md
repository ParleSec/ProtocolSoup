## What this requires

Section 8.3 defines `interval` as "REQUIRED if transaction_id is present" and as "a positive number that represents the minimum amount of time in seconds that the Wallet SHOULD wait after receiving the response before sending a new request to the Deferred Credential Endpoint." Section 9 adds a hard rule for the request itself: "The Wallet MUST present to the Deferred Endpoint an Access Token that is valid for the issuance of the Credential(s) previously requested at the Credential Endpoint."

The statement therefore has two levels. Waiting is a SHOULD; presenting a valid Access Token is a MUST. Section 9.2 says a still-pending Deferred Credential Response returns `interval` and `transaction_id` again with HTTP 202, so the wait applies before every retry.

## Why it exists

Deferred issuance exists for cases such as manual review, where the issuer cannot say exactly when the Credential will be ready. `interval` lets the issuer control how often wallets ask, so one slow review does not turn into a stream of requests. The Access Token rule makes sure that knowing a `transaction_id` is not enough to collect a Credential: the caller must also hold an authorisation for that issuance.

## What non-compliance looks like

A wallet that polls in a tight loop as soon as it gets HTTP 202, ignoring `interval`. Or a wallet that has discarded the original Access Token and polls with a different or expired one, so the issuer rejects the request, or would hand the Credential to a caller who was never authorised for it.

## How ProtocolSoup tests it

When a Credential Response carries `transaction_id`, the wallet calls `waitDeferredInterval`, which sleeps for `interval` seconds, before `pollDeferredCredentialAt` sends the first Deferred Credential Request. For an external issuer it first requires a `deferred_credential_endpoint` in the metadata. Each poll is a POST with the `transaction_id` and the same Access Token and token type used at the Credential Endpoint, with a DPoP proof when the token is DPoP-bound. A still-pending 202 response is retried after its `interval`, or after 5 seconds if it has none, for at most 10 attempts. `positiveIntFromAny` truncates the interval to whole seconds, so a fractional `interval` is waited for less than its value: `1.5` becomes 1 second, and `0.5` means no wait before the first poll. Both are shorter than the minimum Section 8.3 describes.

The registry's evidence, `TestCredentialResponseValueRequiresFinalCredentialsArray`, asserts that `credentialResponseValue` reads the credential from a `credentials` array and rejects the older singular `credential` response shape. It does not exercise `transaction_id`, `interval`, the wait or the Access Token on the deferred request, so it does not prove this statement.
