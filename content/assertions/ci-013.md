## What this requires

OID4VCI 1.0 Appendix F.1 makes `kid`, `jwk` and `x5c` mutually exclusive. For `kid` it says "It MUST NOT be present if jwk or x5c is present", and the same rule is stated for the other two. The issuer side is "The Credential Issuer MUST validate that the JWT used as a proof is actually signed by a key identified in the JOSE Header through either kid, jwk or x5c element."

For the payload, `iss` "MUST be the client_id of the Client making the Credential request. This claim MUST be omitted if the access token authorizing the issuance call was obtained from a Pre-Authorized Code Flow through anonymous access to the token endpoint." Appendix F.1 defines no `cnf` claim for a proof: the key lives in the JOSE header.

## Why it exists

The issued Credential is bound to the proof key, so the issuer must know without doubt which key that is. If a header carries two key references that disagree, the proof could verify under one key while the Credential binds to the other. One reference leaves one key.

The `iss` rule follows from what `iss` means. In an anonymous pre-authorized flow there is no `client_id`, so any `iss` value would be a claim the issuer has no way to check.

## What non-compliance looks like

A Wallet puts both `kid` and `jwk` in the proof header, or sends no key reference at all. A Wallet built for earlier drafts puts the key in payload `cnf.jwk` and sets `iss` and `sub` to its own DID in an anonymous pre-authorized flow. The issuer's response is HTTP 400 with `invalid_proof`.

## How ProtocolSoup tests it

On the issuer side, `proofVerificationKeyFromHeader` in `handlers.go` counts `kid`, `jwk` and `x5c`. If the count is not exactly one, it returns "proof JOSE header must contain exactly one of kid, jwk, or x5c". `jwk` is the only supported reference; `kid` or `x5c` alone are rejected. `parseProofJWK` refuses any private or symmetric key member and any `use` or `key_ops` that is not for signature verification. The proof `alg` must also appear in the configuration's `proof_signing_alg_values_supported`. Every one of these failures is HTTP 400 `invalid_proof`. The access token records the `client_id` it was issued to, which stays empty for a Pre-Authorized Code Token Request sent without one (Appendix G.3.1 calls that anonymous access). After the signature verifies, `validateProofIssuer` rejects an `iss` on an anonymous token, and an `iss` that differs from the token's `client_id`, also with `invalid_proof`. The Credential subject always comes from the access token; `iss` never chooses it. The hosted wallet's HAIP proof sets `iss` to its attested `client_id`.

`TestProofJOSEHeaderRequiresExactlyOneSupportedKeyReference` asserts errors for a header with no reference, `jwk` with `kid`, `kid` alone and `x5c` alone. `TestProofJWKRejectsAllPrivateMaterial` asserts that `d`, `p`, `q`, `dp`, `dq`, `qi`, `oth` and `k` are each rejected. `TestProofAlgorithmMustBeAdvertisedForConfiguration` asserts that an RS256 proof fails against a configuration that lists only ES256. `TestProofIssFollowsClientID` runs the pre-authorized flow end to end and asserts that a proof with no `iss` is accepted with or without a `client_id`, that a matching `iss` is accepted, and that `invalid_proof` is returned for an `iss` on an anonymous token, for a different `client_id`, and for a wallet DID. On the wallet side, `TestCreateCredentialProofJWTUsesFinalAnonymousProofShape` asserts that the hosted wallet's proof has no `iss`, `sub`, `kid` or `cnf` and does have `jwk`. `TestHarnessCreateMdocDeviceProof` asserts that the mdoc device proof verifies against the device key with ES256, has `typ` `openid4vci-proof+jwt` and a `jwk` header, and has no `cnf`.
