## What this requires

This is check 8 of RFC 9449 Section 4.3. Section 4.2 defines `htm` as "The value of the HTTP method (Section 9.1 of [RFC9110]) of the request to which the JWT is attached." The server compares it with the method of the request that actually carried the proof and rejects the proof if they differ.

HTTP method names are case-sensitive (RFC 9110 Section 9.1), so `post` is not `POST`.

## Why it exists

Section 11.1 notes that a captured proof can only be replayed "at the same endpoint (the HTTP endpoint and method are enforced via the respective claims in the JWTs)". The method is one of the two parts of the request the proof covers. Without the check, a proof minted for one operation could be used for another on the same URI, for example a read turned into a write.

## What non-compliance looks like

A server that ignores `htm` accepts a proof minted for `GET` on a `POST` request to the same URI. A server that compares case-insensitively accepts `post` where the client should have sent `POST`, hiding a client bug that a strict server elsewhere will reject.

At a token endpoint the correct response is HTTP 400 with `invalid_dpop_proof` (RFC 9449 Section 5).

## How ProtocolSoup tests it

`dpop.ValidateProof` compares `htm` byte for byte with the request method after upper-casing the method. The token endpoints and the OID4VCI pushed authorization request endpoint pass `POST`, the only method their routes accept. The OAuth 2.0 protected resource and the OID4VCI resource endpoints pass the method of the incoming request.

`TestValidateProofHTMIsCaseSensitiveAgainstUppercasedMethod` signs a proof with `htm` set to `post`, validates it against a `POST` request, and asserts that it is rejected. That shows the comparison is case-sensitive, but it is not a different-method test. `TestValidateProofRejectsHTMMismatch`, in the same file but not listed on this row, validates a `POST` proof against a `GET` request and asserts rejection.
