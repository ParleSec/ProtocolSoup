## What this requires

This is the first half of check 12 of RFC 9449 Section 4.3, which applies when a proof is "presented to a protected resource in conjunction with an access token". The resource server computes the hash of the access token it received and compares it with the proof's `ath` claim. Section 4.2 defines the value: it "MUST be the result of a base64url encoding (as defined in Section 2 of [RFC7515]) the SHA-256 [SHS] hash of the ASCII encoding of the associated access token's value."

A missing `ath` fails this check too, because Section 4.2 makes the claim required in this context.

## Why it exists

Section 11.2 states the reason: "The ath claim limits the use of pre-generated DPoP proofs to the lifetime of the access token." Without it, a proof minted for a resource URI works with any token bound to the same key, including tokens issued later. Section 11.8 adds that the binding relies on the SHA-256 hash being "sufficiently unique so as to reliably identify the access token".

## What non-compliance looks like

A resource server that skips `ath` accepts a valid proof alongside a different access token for the same key. A proof captured or pre-generated while one token was live keeps working after that token is replaced.

The second half of check 12, that the token's bound key matches the proof key, is a separate check.

## How ProtocolSoup tests it

The OAuth 2.0 protected resource and the OID4VCI Credential, deferred credential and notification endpoints pass the access token from the `Authorization: DPoP` header to `dpop.ValidateProof`, which compares base64url(SHA-256(token)) with `ath` in constant time. A mismatch at the OAuth 2.0 protected resource returns HTTP 401 with `invalid_token`; at the OID4VCI endpoints it returns HTTP 401 with `invalid_dpop_proof`. Both carry a `WWW-Authenticate: DPoP` challenge. Token endpoints do not pass an access token, so `ath` is not required there.

`TestValidateProofATHMustMatchAccessToken` signs a proof whose `ath` is the hash of one token, asserts that it validates with that token, and asserts that it is rejected when a different token is supplied. No registry test covers a proof with `ath` missing.
