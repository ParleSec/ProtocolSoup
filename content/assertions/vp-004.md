## What this requires

A verifier can pass its Authorization Request by reference, as a `request_uri` the wallet fetches. Section 5.1 says that when `request_uri_method` is `get`, "the Wallet MUST send the request to retrieve the Request Object using the HTTP GET method, i.e., as defined in [RFC9101]", and when the parameter is absent "the Wallet MUST process the request_uri parameter as defined in [RFC9101]."

For the POST method, Section 5.10.1 sets the response shape: "The Request URI response MUST be an HTTP response with the content type application/oauth-authz-req+jwt and the body being a signed, optionally encrypted, request object as defined in [RFC9101]." ProtocolSoup serves GET retrieval the same way. The response body is the compact JWS, with no JSON object or other wrapper, and the media type is the one RFC 9101 registers for Request Objects.

## Why it exists

The wallet must verify the signature over exactly the bytes the verifier signed, and it must know what it is parsing before it parses it. A request object wrapped in a JSON envelope is not a Request Object, so a wallet that follows RFC 9101 cannot find the JWT in it. The media type lets the wallet reject a response that is not a Request Object before any decoding happens.

## What non-compliance looks like

A verifier returns `Content-Type: application/json` with a body such as `{"request":"eyJ..."}`. A standards-following wallet either rejects the response or tries to decode the JSON text as a JWT and fails. On the wallet side, the fault is the reverse: accepting any media type, or pulling a JWT out of whatever body arrives, so the wallet no longer checks that the verifier returned a Request Object.

## How ProtocolSoup tests it

On the verifier, `handleGetAuthorizationRequest` (`backend/internal/protocols/oid4vp/handlers.go`) answers `GET /oid4vp/request/{requestID}` with status 200, `Content-Type: application/oauth-authz-req+jwt` and the stored compact JWT as the body. Before that it returns 404 `invalid_request_uri` for an unknown request, 405 `invalid_request` with `Allow: POST` when the request was created with `request_uri_method=post`, 400 `invalid_request_uri` once the request has expired, and 400 `invalid_request_object` if the stored object's `typ` is not `oauth-authz-req+jwt`. On the wallet, `fetchRequestObject` (`backend/cmd/walletharness/main.go`) sends `Accept: application/oauth-authz-req+jwt`, rejects any non-2xx status and any other media type, and requires a body with exactly two dots. That last check means it also rejects an encrypted request object, which Section 5.10.1 allows on the POST path.

`TestAuthorizationRequestGETReturnsCompactJWTBody` creates a `direct_post` request, fetches its `request_uri` with GET, and asserts status 200, a `Content-Type` of exactly `application/oauth-authz-req+jwt`, and a body equal to the `request` JWT the create call returned. `TestFetchRequestObjectConsumesFinalCompactJWTBody` runs a test server that asserts the wallet used GET with the `Accept` header above, serves the JWT with the correct media type, and asserts that `fetchRequestObject` returns that JWT unchanged. Neither test covers the wallet rejecting a wrong media type or a wrapped body.
