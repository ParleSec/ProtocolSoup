## What this requires

OID4VCI 1.0 Section 11 lets the Wallet report what happened to issued Credentials. The `event` value "MUST be a case sensitive string whose value is either credential_accepted, credential_failure, or credential_deleted." The endpoint is idempotent: "When the Credential Issuer receives multiple identical calls from the Wallet for the same notification_id, it returns success." Section 11.3 adds: "When the notification_id value is invalid, the HTTP response MUST use the HTTP status code 400 (Bad Request)".

The specification does not say in so many words that a `notification_id` belongs to one Access Token. ProtocolSoup treats a `notification_id` presented with any token other than the one that issued it as invalid.

## Why it exists

Section 11 is explicit about the network: "Due to the network errors, there are no guarantees that a Credential Issuer will receive a notification within a certain time period or at all." A Wallet that did not get a response will retry, so the retry must not count as a second event.

Without the token binding, a `notification_id` would be a bearer handle to someone else's issuance state. Any Wallet holding a valid token could mark another Wallet's Credentials as deleted or failed.

## What non-compliance looks like

An issuer that compares `event` case-insensitively accepts `Credential_Accepted`. An issuer that appends every call to its log records one acceptance twice. An issuer that looks up `notification_id` without the token lets one Wallet report on another Wallet's issuance. The correct error codes are `invalid_notification_id` and `invalid_notification_request`, both with HTTP 400.

## How ProtocolSoup tests it

`handleNotification` in `handlers.go` returns HTTP 401 with `invalid_token` when the token is missing or invalid. These requests get HTTP 400 with `invalid_notification_request`: a non-JSON media type, a repeated parameter, a missing `notification_id`, an unknown `event`, or an `event_description` with characters outside `%x20-21 / %x23-5B / %x5D-7E`. An unknown `notification_id`, or one created under another token, gets HTTP 400 with `invalid_notification_id`. A first event, or an identical retry, returns HTTP 204, and a retry adds no new event.

ProtocolSoup also applies its own state rule. `credential_accepted` may be followed by `credential_deleted`, but a conflicting terminal event such as `credential_failure` after an acceptance is rejected with `invalid_notification_request`. Section 11.3 leaves what happens after an error to the issuer.

`TestNotificationEndpointMutatesStateAndIsIdempotent` posts the same `credential_accepted` twice. It asserts 204 both times, exactly one stored event, and two Looking Glass events, the second marked `idempotent_retry`. `TestNotificationEndpointRejectsInvalidRequestsAndCrossTokenID` asserts 400 and the error code for a wrong-case event, a newline in `event_description`, an unknown ID, and an ID presented with another token. It also asserts 401 when no token is sent. `TestNotificationRejectsConflictingTerminalEvent` asserts 204 for acceptance, 400 `invalid_notification_request` for a following `credential_failure`, and 204 for `credential_deleted`.
