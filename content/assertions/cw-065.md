## What this requires

Appendix F.1 opens with "The JWT MUST contain the following elements". In the JOSE header, `alg` "MUST NOT be none or an identifier for a symmetric algorithm (MAC)" and `typ` "MUST be openid4vci-proof+jwt". The key is named by one of `kid`, `jwk` or `x5c`, and each "MUST NOT be present" alongside either of the others. In the body, `aud` "MUST be the Credential Issuer Identifier", `iat` is REQUIRED, and `nonce` "MUST be present when the issuer has a Nonce Endpoint as defined in Section 7."

The proof shows that the wallet holds the private key the Credential will be bound to. The issuer binds the Credential to the key named in the header, so that key has to be unambiguous.

## Why it exists

Section 13.8 explains the freshness parts: an adversary who obtains a key proof "could potentially replay that proof to a Credential Issuer to obtain a duplicate Credential", and "The c_nonce parameter serves as the main defense against this". `aud` stops a proof made for one issuer being replayed at another. The `typ` value, per F.1, "explicitly types the key proof JWT as recommended in Section 3.11 of [RFC8725]", so the proof cannot be confused with another JWT signed by the same key. An asymmetric `alg` matters because a MAC proves knowledge of a shared secret, not possession of a private key. Allowing only one key reference means the issuer and the wallet cannot disagree about which key was bound.

## What non-compliance looks like

A proof with `typ: JWT`, or with both `kid` and `jwk` in the header (often a library adding a default `kid`), or with no `nonce` after the wallet called the Nonce Endpoint. An `aud` set to the Credential Endpoint URL instead of the Credential Issuer Identifier. Section 8.3.1.2 gives the issuer's error: `invalid_proof`, "The proofs parameter in the Credential Request is invalid".

## How ProtocolSoup tests it

The wallet builds proofs in `createCredentialProofJWT`, its batch and `mso_mdoc` variants, and `createCredentialProofJWTWithKeyAttestation` on the HAIP path. All of them set `typ: openid4vci-proof+jwt`, put the holder key in the `jwk` header, and set `aud` to the Credential Issuer Identifier from metadata, `iat`, and `nonce` from the Nonce Endpoint. They sign with ES256, RS256 or EdDSA. `walletSignToken` leaves out its default `kid` when the caller supplies `jwk`. The wallet refuses to build a proof without a `c_nonce`, and stops if an issuer requires a `jwt` proof but has no `nonce_endpoint`.

`TestCreateCredentialProofJWTUsesFinalAnonymousProofShape` builds a proof with `createCredentialProofJWT` and asserts that the header carries `jwk` and no `kid`, and that the body has no `iss`, `sub` or `cnf`. It does not assert `typ`, `alg`, `aud`, `iat` or `nonce`, and it does not cover the HAIP proof builder. Those parts of the statement are visible in the code but not proven by this test.
