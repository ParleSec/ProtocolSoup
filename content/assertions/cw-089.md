## What this requires

Section 14.5 describes two ways to update an issued Credential. The first: "the Wallet may receive an updated version of a Credential from a Credential Endpoint using a valid Access Token. This does not involve interaction with the End-User. If the Credential Issuer issued a Refresh Token to the Wallet, the Wallet would obtain a fresh Access Token by making a request to the Token Endpoint, as defined in Section 6 of [RFC6749]." The second is reissuance from the beginning, and "A Credential needs to be reissued if the Wallet does not have a valid Access Token or a valid Refresh Token."

Section 14.5 is an Implementation Consideration and uses no BCP 14 keywords: it describes the mechanism rather than mandating it. The registry records it at MAY, the level that matches an option the specification describes without requiring.

## Why it exists

Claim values and issuer signatures change after issuance: an address moves, a signing key rotates, a Credential nears expiry. A Refresh Token lets the wallet fetch an updated Credential silently. Without one, the only path is the full issuance flow, which brings the End-User back in. Section 14.5 also warns that after reissuance the wallet may need to delete the old Credential, "Otherwise, the Wallet might end up with more than one Credential of the same type, without knowing which one is the latest."

## What non-compliance looks like

A wallet that discards the `refresh_token` from the Token Response and sends the user through the whole issuance flow each time a Credential expires. Or a wallet that keeps retrying the Credential Endpoint with an expired Access Token instead of using its Refresh Token. Or a wallet that reissues without removing the superseded Credential.

## How ProtocolSoup tests it

When a Token Response carries a `refresh_token`, the hosted wallet keeps it with the Credential it binds, together with the issuer and Authorization Server metadata, the configuration, and the client authentication of the original grant: the same `client_id` and `client_secret`, or on the HAIP path the same client attestation and DPoP key, which a DPoP-bound refresh token must be presented with (RFC 9449 Section 5). `POST /api/refresh` redeems it with `grant_type=refresh_token` at the Token Endpoint (RFC 6749 Section 6), then requests the Credential again with the fresh Access Token, with no End-User interaction. The new Credential replaces the old one, so the wallet does not hold two of the same type. If the Token Response carries a new `refresh_token`, the old one is discarded, as RFC 6749 Section 6 requires. Without a Refresh Token, `/api/refresh` answers 400 and points to reissuance; the wallet also reissues from the start when a held Credential is within 90 seconds of expiry (`credentialRefreshRequired`, then `issueCredentialForWallet`), which is the second mechanism in Section 14.5. ProtocolSoup's issuer returns a `refresh_token` on the authorization_code grant only.

`TestAPIRefreshReissuesCredentialWithRefreshToken` runs an authorization_code import against a local issuer that returns a `refresh_token`, then calls `/api/refresh`. It asserts that the refresh grant carries the kept token and the original `client_id`, that the Credential Request uses the fresh Access Token, that the new Credential replaces the old one, and that the rotated `refresh_token` is kept. It also asserts that a Credential without a Refresh Token is refused with a pointer to reissuance. `TestExchangeRefreshTokenAuthenticatesAsTheOriginalGrant` asserts the grant carries the original `client_id` and `client_secret`, and `TestExchangeRefreshTokenRequiresInputs` asserts it refuses an empty token endpoint or refresh token.
