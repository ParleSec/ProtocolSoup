## What this requires

HAIP 1.0 Section 7 states: "Issuers, Verifiers, and Wallets MUST, at a minimum, support ECDSA with P-256 and SHA-256 (JOSE algorithm identifier ES256; COSE algorithm identifier -7 or -9, as applicable) for the purpose of validating the following:". The list that follows is split by role. Wallet Attestations including PoP, Key Attestations and the `jwt` proof type sit under Issuers, because the Issuer validates them. Under Wallets the list is "signed presentation requests." and "signed Issuer metadata."

So for a wallet the floor is being able to verify an ES256 signature on a signed OpenID4VP request object, and on signed Credential Issuer Metadata where an ecosystem requires it (HAIP Section 4.1). The wallet may support more algorithms, but it cannot lack ES256.

## Why it exists

HAIP does not give a reason in the text. A profile meant for interoperability needs one algorithm every party can verify. Without it, two conformant implementations could each support a different suite and never be able to check each other's signatures. ES256 over P-256 is the suite HAIP names as that common minimum.

## What non-compliance looks like

A wallet that accepts only RS256 or EdDSA request objects cannot verify an ES256-signed `x509_hash` request from a HAIP Verifier and has to refuse a valid presentation request. A wallet that silently skips the signature check when it does not recognise `alg` is worse: it accepts requests it never verified.

## How ProtocolSoup tests it

The hosted wallet verifies `x509_hash` and `x509_san_dns` request objects in `verifyX509HashRequestObjectSignature` and `verifyX509SANDNSRequestObjectSignature`. Each validates the `x5c` chain against the wallet's own roots, then calls `verifyCompactJWTSignature` with the leaf public key. That uses `jwt.Parse`, which verifies ES256 with a P-256 key and fails on any signature mismatch. It does not restrict `alg` to an allow-list beyond what the key type permits. The wallet does not process signed Credential Issuer Metadata. On the issuance side it produces ES256 signatures for its Wallet Attestation, PoP, key attestation, proofs and DPoP; it does not validate them.

The registry tests do not exercise ES256 validation. `TestGenerateEphemeralEncryptionKeyIsP256` generates a key with the Go standard library and asserts its curve is P-256, without calling wallet code. `TestHAIPAttestationJWTBuildersUseExpectedHeaders` builds the Wallet Attestation, PoP, key attestation and proof JWTs and asserts their `typ` headers and claims. That is signing evidence, and it does not assert `alg`.
