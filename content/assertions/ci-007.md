## What this requires

When `authorization_details` of type `openid_credential` is used in the Authorization Request or Token Request, the Token Response returns it with `credential_identifiers`. OID4VCI 1.0 Section 6.2 defines that member as "A non-empty array of strings, each uniquely identifying a Credential Dataset that can be issued using the Access Token returned in this response", and says "The Wallet MUST use these identifiers together with an Access Token in subsequent Credential Requests."

Section 8.2 sets the Credential Request side. `credential_identifier` is "REQUIRED when an Authorization Details of type openid_credential was returned from the Token Response. It MUST NOT be used otherwise." `credential_configuration_id` and `credential_identifier` are mutually exclusive.

## Why it exists

A `credential_identifier` is a reference to a Credential Dataset that one Access Token authorised. If the issuer resolves it without checking which token it came from, a Wallet holding a token for one dataset can request a dataset authorised under a different token, for example by reusing an identifier it saw in another session. Binding identifiers to the token that returned them closes that path.

## What non-compliance looks like

An issuer that keeps one global identifier table accepts an identifier minted for a different token. An issuer that falls back to `credential_configuration_id` after it has returned identifiers lets the Wallet bypass the dataset the Authorization Server selected. Under Section 8.3.1.2 these requests should fail with `unknown_credential_identifier` or `invalid_credential_request`.

## How ProtocolSoup tests it

At the token endpoint, `createCredentialAuthorization` mints one random identifier for each authorised configuration and stores the mapping on the access grant. This happens for the pre-authorized and authorization code grants. At the Credential Endpoint, a request that sends both parameters gets `invalid_credential_request`. An identifier that is not on this token's grant gets `unknown_credential_identifier`. A `credential_configuration_id` on a token that returned identifiers gets `invalid_credential_request` ("credential_identifier is required for this access token"). All of these are HTTP 400.

`TestAuthorizationDetailsIssuesTokenBoundCredentialIdentifiers` offers two configurations and requests one through `authorization_details`. It asserts that exactly one `authorization_details` item comes back, that a Credential Request using that identifier returns HTTP 200 with a Credential and a `notification_id`, and that the response has no singular `credential`. `TestCredentialIdentifierRejectsMixedUnknownAndCrossTokenValues` asserts the error code for four requests: both parameters together, an unknown identifier, an identifier from a second token, and `credential_configuration_id` after identifiers were returned. `TestAuthorizationCodeGrantReturnsCredentialIdentifiers` asserts that the authorization code grant records the returned identifier on the real access grant. It then replays the code and asserts that the token is revoked and that the Credential Endpoint answers with `invalid_token`.
