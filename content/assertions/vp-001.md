## What this requires

OpenID4VP 1.0 carries the Client Identifier Prefix inside `client_id` itself, joined to the original identifier by a colon. Section 5.9.1 says "Wallets MUST use the presence of a : (colon) character and the content preceding it to determine whether a Client Identifier Prefix is used", and fixes which colon counts: "The Client Identifier Prefix is defined as the string before the (first) : character." If that string is a recognized and supported prefix, the wallet MUST interpret the identifier by that prefix's rules. With no colon at all, Section 5.9.2 makes it a pre-registered client.

The prefix is the only input. OpenID4VP 1.0 defines no separate request parameter for it, so the `client_id_scheme` parameter from earlier drafts plays no part in the decision.

## Why it exists

Section 14.8 states the risk directly: "Confusing Verifiers using a Client Identifier Prefix with those using none can lead to attacks." The prefix decides how the wallet authenticates the verifier. `x509_san_dns` and `x509_hash` require a request signed by a key in a validated X.509 chain, `decentralized_identifier` requires a key from the DID Document, and `redirect_uri` requests cannot be signed at all. A wallet that takes this decision from anything other than the identifier lets the request choose a weaker check than the one its `client_id` names.

Section 5.9.1 also warns that "implementations should not assume that the presence of a : character implies that the entire value can be processed as a valid URI." Each prefix has its own parsing rules for the part after the colon.

## What non-compliance looks like

A wallet that still reads a `client_id_scheme` parameter can receive `client_id=x509_hash:...` together with `client_id_scheme=redirect_uri` and skip the certificate check that `x509_hash` requires. A wallet that splits on the last colon reads `redirect_uri:https://verifier.example/cb` as the prefix `redirect_uri:https`, which is not a prefix at all. A wallet that parses the whole value as a URI treats `x509_san_dns:client.example.org` as a URI with the scheme `x509_san_dns` and applies URI rules to a DNS name.

## How ProtocolSoup tests it

The hosted wallet classifies the `client_id` of every request object in `inferClientIDScheme` (`backend/cmd/walletharness/main.go`). It matches the six prefixes Section 5.9.3 defines for requests, each including its colon, against the start of the value. A value with no colon, or one that starts with `http:`, `https:` or `did:`, is treated as pre-registered. Any other value of the form name, colon, rest is classified as unknown, and the wallet refuses the request with `unsupported client_id scheme prefix`. The function receives the request payload as a parameter but never reads it.

`TestInferClientIDSchemeUsesClientIDPrefixOnly` asserts that `x509_san_dns:` and `verifier_attestation:` identifiers map to their prefixes, that `x509_hash:thumbprint` stays `x509_hash` when the payload carries `client_id_scheme: redirect_uri`, that an `https` URL and a `did:web` identifier stay pre-registered when the payload names a different scheme, and that `invalid_scheme:attacker` is unknown. `TestParseClientIDSchemeUsesFinalPrefixFallback` covers `ParseClientIDScheme` in `backend/internal/protocols/oid4vp/contracts.go`, which the verifier uses to classify the `client_id` of requests it creates. It asserts the same first-colon rule: bare and URL identifiers are pre-registered, `redirect_uri:` and `x509_hash:` are recognised, `:example-client` and `redirect_uri :...` are not prefixes, and a blank value is an error. That second test exercises verifier code, not the wallet.
