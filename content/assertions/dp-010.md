## What this requires

This is check 11 of RFC 9449 Section 4.3. The server decides when the proof was created, either from its `iat` claim or from a timestamp the server built into a nonce it issued, and rejects the proof if that time falls outside a window the server accepts. Section 4.3 points to Section 11.1 for what the window should be.

The spec does not fix the window's size. It does say that servers "MAY accept DPoP proofs that carry an iat time in the reasonably near future (on the order of seconds or minutes)" to allow for clock offsets.

## Why it exists

Section 11.1 states the reason: a captured proof can be replayed at the same endpoint, so "servers MUST only accept DPoP proofs for a limited time after their creation (preferably only for a relatively brief period on the order of seconds or minutes)." The window also bounds how long a server must remember each `jti` to detect replays.

## What non-compliance looks like

A server that never checks `iat` accepts a proof minted hours ago, or one stamped days in the future by a client that pre-generated it. Its replay cache then has to hold `jti` values indefinitely or it lets replays through once an entry expires.

At a token endpoint the correct response is HTTP 400 with `invalid_dpop_proof` (RFC 9449 Section 5).

## How ProtocolSoup tests it

ProtocolSoup uses `iat` only. Its nonces are random values with no timestamp in them, so they do not take part in this check. `dpop.ValidateProof` requires `iat` to be a NumericDate and rejects it if it is more than 60 seconds before or after the server's current time. The replay store keeps each `jti` until `iat` plus the same 60 seconds.

`TestValidateProofRejectsStaleIat` signs a proof with `iat` 61 seconds in the past and asserts rejection. `TestValidateProofRejectsFutureIat` signs one with `iat` 61 seconds in the future and asserts rejection.
