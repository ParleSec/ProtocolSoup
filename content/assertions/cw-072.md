## What this requires

Section 8.2: "The Client MAY request encrypted responses by providing its encryption parameters in the Credential Request when encryption_required is false and MUST do so when encryption_required is true. Credential Request encryption MUST be used if the credential_response_encryption parameter is included, to prevent it being substituted by an attacker." The `credential_response_encryption` object carries the wallet's public `jwk` and the `enc` algorithm, both REQUIRED.

Section 10 sets the format for both directions: "The contents of the message MUST be encoded as a JWT as described in [RFC7519]. The media type MUST be set to application/jwt." In the chosen key, "The alg parameter MUST be present", and "The JWE alg algorithm used MUST be equal to the alg value of the chosen JWK." The same rules apply at the Deferred Credential Endpoint.

## Why it exists

Section 13.11 says that encryption beyond TLS "can offer enhanced data confidentiality", especially where the wallet has components with different levels of trust, such as a backend and a client application. The request must be encrypted as well because the response key travels in the request. An attacker who could change a plaintext request could replace that key with their own and read the Credential when it comes back.

## What non-compliance looks like

The issuer's metadata sets `credential_response_encryption.encryption_required` to true and the wallet sends no `credential_response_encryption`. The issuer then returns `invalid_encryption_parameters`, which Section 8.3.1.2 says "indicates that the Credential Issuer requires the Credential Response to be sent encrypted, but the Credential Request does not contain the necessary encryption parameters." Other forms: the wallet sends its response key in a plaintext JSON request, or cannot parse an `application/jwt` response and fails after the Credential has been issued.

## How ProtocolSoup tests it

`buildCredentialRequestBody` adds `credential_response_encryption` when the metadata sets `encryption_required`, or when the caller asks for it; the HAIP path asks whenever the issuer advertises response encryption and request-encryption keys. `buildCredentialResponseEncryptionObject` requires the issuer to advertise `ECDH-ES` and `A256GCM` or `A128GCM`, generates a fresh P-256 key, and sends its JWK with `alg: ECDH-ES` and `use: enc`. With a response key in the body, `requestCredentialWithLifecycle` encrypts the whole request to the issuer's `credential_request_encryption` key as `application/jwt`, and stops with an error if the metadata has no such key. An `application/jwt` response is decrypted by `decryptCredentialResponseJWT`, which accepts only `ECDH-ES` with `A128GCM` or `A256GCM`. `pollDeferredCredentialAt` does the same for deferred requests. A plaintext JSON response to an encrypted request is still accepted; Section 10 says such a message "SHOULD be rejected".

`TestCredentialResponseEncryptionJWERoundTrip` builds the encryption object with `encryption_required` set and parses the JWK the wallet would send. It encrypts a `credentials` payload to that key with `ECDH-ES` and `A256GCM`, and asserts that `decryptCredentialResponseJWT` returns the credentials. It covers response decryption only. It does not cover request encryption, the `Content-Type` handling, or the deferred path.
