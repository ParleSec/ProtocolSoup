## What this requires

OID4VCI 1.0 Section 8.2 defines `proofs` as OPTIONAL. The OPTIONAL level is about whether the parameter is sent at all. When it is sent, its shape is fixed: a JSON object with exactly one member, named after a proof type from Appendix F (`jwt`, `di_vp` or `attestation`), whose value is a non-empty array. For the `jwt` type, Appendix F says the object "MUST include a jwt parameter with its value being a non-empty array of JWTs".

Being OPTIONAL does not make the parameter optional for every request. Section 8.2 also says "The proofs parameter MUST be present if the proof_types_supported parameter is present in the credential_configurations_supported parameter of the Issuer metadata for the requested Credential."

## Why it exists

The number of array elements is the number of keys the Wallet wants Credentials bound to. Section 8.3 uses that count to bound the response: the number of `credentials` "matches the number of keys that the Wallet has provided via the proofs parameter of the Credential Request, unless the Issuer decides to issue fewer Credentials." With one proof type per request, every key is checked under one set of rules and the key count is unambiguous.

## What non-compliance looks like

Wallets written against earlier drafts send `proofs` as an array of `{"proof_type": "jwt", "jwt": "..."}` objects, or send a singular `proof` object instead. Other malformed shapes are an empty array (`{"jwt": []}`) or two proof types in one object (`{"jwt": [...], "di_vp": [...]}`). An issuer that tolerates these has to guess which keys to bind and how many Credentials to issue.

ProtocolSoup rejects each of these with HTTP 400 and `invalid_proof`. The error descriptions are "proofs must be an object keyed by proof type", "proofs must contain exactly one proof type" and "proofs.jwt must be a non-empty array". `jwt` is the only proof type the issuer accepts; any other name gets "unsupported proof type". A request with no `proofs` at all also gets `invalid_proof`, because the handler always requires proofs.

## How ProtocolSoup tests it

The Credential Endpoint passes the raw `proofs` value to `collectProofs` in `handlers.go`, which decodes it as an object of arrays and applies the rules above before any proof JWT is parsed.

`TestCredentialRequestRejectsArrayProofsShape` obtains a pre-authorized access token, sends `proofs` as an array of `proof_type`/`jwt` objects, and asserts HTTP 400 with `invalid_proof`. This test covers the array shape only. The empty-array and two-proof-type rules are in `collectProofs`, but no test listed for this requirement exercises them.
