## What this requires

Section 12.2.4 says the presence of `batch_credential_issuance` "means that the issuer supports more than one key proof in the proofs parameter in the Credential Request". Its `batch_size` is the "maximum array size for the proofs parameter in a Credential Request. It MUST be 2 or greater." Section 8.3 bounds the binding: "Each key provided by the Wallet is used to bind to, at most, one Credential." Section 3.3.2 says the batch "MUST share the same Credential Format and Credential Dataset, but SHOULD contain different Cryptographic Data."

For request parsing, Section 8.2 has the issuer ignore unrecognised parameters. Section 8.3.1.2 defines `invalid_credential_request` to include a request that "repeats the same parameter".

## Why it exists

Section 3.3.2 gives the reason for distinct keys: "to achieve unlinkability between the Credentials, each credential should be bound to different cryptographic keys." A batch of Credentials bound to one key can be correlated every time any of them is presented. The `batch_size` cap gives the issuer a published upper bound on the work one request can demand.

## What non-compliance looks like

An issuer that accepts the same proof twice issues two Credentials bound to one key. An issuer that ignores `batch_size` signs as many Credentials as the Wallet sends proofs. A parser that keeps the last copy of a repeated member reads a different request from the one a proxy or logger saw.

## How ProtocolSoup tests it

The metadata advertises `batch_credential_issuance` with `batch_size` 20. `collectProofs` in `handlers.go` rejects more than 20 `jwt` proofs with HTTP 400 `invalid_proof`. Each proof is validated, and a JWK thumbprint already seen in the request is rejected with `invalid_proof`. Rejecting is ProtocolSoup's way to satisfy "at most one Credential" per key; Section 14.6 would also let an issuer issue fewer. All proofs must carry the same `c_nonce`. One Credential is issued per proof, with `cnf.jwk` set to that proof's key. `decodeRequestObject` rejects any repeated member name, known or unknown, with `invalid_credential_request` and drops unknown members. The Notification Request decoder applies the same rules with `invalid_notification_request`.

`TestCredentialIssuesBatchBoundToDistinctProofKeys` sends two proofs with different keys and asserts two Credentials with two distinct `cnf.jwk` thumbprints and one shared `sub` and `vct`. `TestCredentialRejectsDuplicateProofKeysInBatch` sends one proof twice and asserts 400 `invalid_proof`. `TestCredentialRejectsProofsExceedingBatchSize` sends 21 proofs and asserts 400 `invalid_proof`. `TestDeferredRequestIgnoresUnknownParametersAndRejectsDuplicates` and `TestDecodeNotificationRequestRejectsDuplicatesAndIgnoresUnknownParameters` are decoder unit tests: an extension member is ignored and a repeated `transaction_id` or `notification_id` is an error. None of the five tests sends a repeated member to the Credential Endpoint itself.
