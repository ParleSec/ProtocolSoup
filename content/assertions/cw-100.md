## What this requires

Section 15.3: "Wallets SHOULD store Credentials only in encrypted form, and, wherever possible, use hardware-backed encryption. Wallets SHOULD not store Credentials longer than needed." These are two separate SHOULDs: encryption at rest, with hardware-backed keys where the platform has them, and a retention limit.

Both are recommendations, not requirements. A wallet that does not follow them is expected to have a reason and to state it.

## Why it exists

The section opens with its reason: "To prevent a leak of End-User data, especially when it is signed, which risks revealing private data of End-Users to third parties, systems implementing this specification SHOULD be designed to minimize the amount of End-User data that is stored." A signed Credential is portable evidence. Anyone who copies it out of storage can show the claims to a third party with the issuer's signature attached, so stored copies are worth protecting and worth deleting once they are no longer needed.

## What non-compliance looks like

Credentials written as plaintext to a database, a file or a browser store, readable by anything with access to that storage. Credentials kept indefinitely after the user stops using them, or copied into logs and backups that outlive the wallet entry.

## How ProtocolSoup tests it

The hosted wallet deviates from the encryption recommendation, and records the decision in `docs/packages/wallet.md`; there is no separate ADR file. Credentials are held in process memory per session scope key, unencrypted, and nothing is written to disk. Wallet sessions expire after `WALLET_SESSION_TTL` of inactivity (default 20 minutes), and an expired session is removed the next time the store is accessed. Nothing survives a restart except the mdoc device key at `WALLET_DEVICE_KEY_PATH`, which is a key, not a Credential. The retention recommendation is therefore partly met: Credentials live only for the session. Hardware-backed encryption is not used. The documented reason is that durable encrypted storage is deferred until the platform vault initiative, because a temporary Fly-backed vault would be thrown away once storage moves to HashiCorp. The same in-memory store backs OID4VP presentations, which the registry treats as a cross-protocol limitation, not an OID4VP deviation.

`TestIso18045ModerateNotClaimedWhenEnvUnset` asserts that the wallet's key attestation carries no `key_storage` or `user_authentication` levels unless `WALLET_KEY_ATTESTATION_KEY_STORAGE` and `WALLET_KEY_ATTESTATION_USER_AUTHENTICATION` are set, and carries `iso_18045_moderate` only when they are. This shows that the software wallet does not claim hardware-grade key protection it cannot prove. It does not test how Credentials are stored or how long they are kept.
