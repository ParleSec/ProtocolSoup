## What this requires

Section 6 says the Token Endpoint "is used in the same manner as defined in [RFC6749]". RFC 6749 Section 4.1.2 requires the authorization server to deny a second use of an authorization code, and says it SHOULD revoke the tokens already issued from that code. For deferred issuance, OID4VCI 1.0 Section 9.1 says "The Credential Issuer MUST invalidate the transaction_id after the Credential for which it was meant has been obtained by the Wallet."

Section 9.3 defines the error for a spent identifier. `invalid_transaction_id` "occurs when the transaction_id was not issued by the respective Credential Issuer or it was already used to obtain a Credential." The "at most once" rule has to hold when two redemptions arrive together, not only when they arrive one after the other.

## Why it exists

Both values are one-time handles to something already authorised: a code to an Access Token, a `transaction_id` to Credentials prepared for one request. If either can be redeemed twice, an intercepted copy yields a second token or a second set of Credentials. The race case matters because a check-then-delete that is not atomic lets both requests pass the check.

## What non-compliance looks like

Two concurrent Token Requests with the same `code` both return HTTP 200. Two concurrent Deferred Credential Requests with the same `transaction_id` both return the Credentials. The correct losing responses are HTTP 400 `invalid_grant` at the Token Endpoint and HTTP 400 `invalid_transaction_id` at the Deferred Credential Endpoint.

## How ProtocolSoup tests it

The Mock IdP's `ValidateAuthorizationCode` deletes the code and records it as used under one lock. A replay is refused, the access tokens issued from the code are revoked and its refresh tokens are dropped, and the OID4VCI token handler reports the refusal as HTTP 400 `invalid_grant`. `handleDeferredCredential` checks readiness and token ownership and deletes the transaction under the same lock. The losing request gets HTTP 400 `invalid_transaction_id`, and a transaction presented with a different Access Token gets HTTP 403 `invalid_token`.

`TestAuthorizationCodeRedemptionIsAtomic` sends two concurrent Token Requests with one authorization code. It asserts exactly one HTTP 200 and one HTTP 400 with `invalid_grant`. `TestDeferredIssuanceFlow` makes a deferred Credential Request and asserts HTTP 202 with a `transaction_id` and no `notification_id`. After the ready delay it sends two concurrent Deferred Credential Requests and asserts exactly one HTTP 200, carrying a Credential and a `notification_id`, and one HTTP 400 `invalid_transaction_id`.
