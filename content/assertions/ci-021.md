## What this requires

An issuer that publishes `credential_request_encryption` in its metadata takes on an obligation. That object holds a `jwks` in which "Each JWK in the set MUST have a kid (Key ID) parameter that uniquely identifies the key", plus `enc_values_supported` and `encryption_required` (Section 12.2.4). The issuer has to accept requests encrypted under those parameters. Section 10 fixes the encoding: "The contents of the message MUST be encoded as a JWT as described in [RFC7519]. The media type MUST be set to application/jwt."

Once decrypted, the request is a normal Credential Request. Every Section 8.2 rule applies to it as it would to an `application/json` body.

## Why it exists

Section 13.11 frames encryption as protection for architectures where TLS ends before the component that handles the request. It warns that "In cases where the application-layer encryption begins and terminates in the same component as TLS, it provides no additional protection." Whatever the deployment, a decrypted request that skips validation is worse than no encryption. Every check the JSON path applies has to apply after decryption too.

## What non-compliance looks like

An issuer advertises a key or an `enc` value its decryptor does not accept, so every encrypted request fails. Or the encrypted path has its own parser that skips the duplicate-member, proof or `credential_identifier` checks, so encryption becomes a way around validation.

## How ProtocolSoup tests it

`credentialRequestEncryptionMetadata` in `credential_request_encryption.go` publishes one P-256 JWK with `kid` `oid4vci-credential-request-encryption`, `alg` `ECDH-ES` and `use` `enc`. It sets `enc_values_supported` to `A128GCM` and `A256GCM` and `encryption_required` to `false`, and lists no `zip_values_supported`. `decodeJSONOrEncryptedJWTRequest` takes an `application/jwt` body of up to 64 KiB and parses it, allowing only `ECDH-ES` with those two `enc` values. It decrypts with the matching private key, which the issuer keeps for this purpose only: it is not the mdoc Document Signer key that signs IssuerAuth, signed metadata and status lists. With `SHOWCASE_MDOC_PKI_PATH` (or the data directory) set, the key is stored as `credential_request_encryption_key.pem` beside the mdoc PKI so a restart keeps the advertised key. The decoder then passes the plaintext to the same `decodeRequestObject` used for JSON. Any parse or decryption failure is HTTP 400 `invalid_credential_request`. The Deferred Credential Endpoint uses the same path. The decoder also reports whether the body arrived encrypted, and a plaintext request that carries `credential_response_encryption` is refused with `invalid_encryption_parameters` (CI-022).

`TestCredentialRequestEncryptionKeyIsDedicated` asserts that the key differs from the Document Signer key, that the metadata advertises exactly that key with `use` `enc`, that a request encrypted to the Document Signer key does not decrypt, and that a configured store returns the same key after a reload. `TestCredentialRequestEncryptionRoundTrip` builds a Credential Request with a fresh `c_nonce` and a proof and encrypts it with `ECDH-ES` and `A128GCM`. It posts the result as `application/jwt` and asserts HTTP 200 with an issued Credential. It takes the recipient public key straight from the plugin's document signer key instead of reading the advertised `jwks`. It does not try `A256GCM` or an unadvertised algorithm.
