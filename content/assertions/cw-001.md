## What this requires

Section 4.1 says "The Credential Offer contains a single URI query parameter, either credential_offer or credential_offer_uri". Each definition then carries the prohibition: `credential_offer` "MUST NOT be present when the credential_offer_uri parameter is present", and `credential_offer_uri` "MUST NOT be present when the credential_offer parameter is present."

The rule constrains how an offer is built. For the wallet it means an offer carrying both parameters is malformed, and the wallet refuses it rather than deciding which one to honour.

## Why it exists

The two parameters are alternative transports for the same object: the offer inline by value, or an `https` URL the wallet fetches to get it (Section 4.1.3). When both arrive they can describe different offers, with different issuers, configurations or grants. Which one a wallet then acts on depends only on the order its parser checks them, so two wallets can process the same link differently. Refusing the offer removes the choice.

## What non-compliance looks like

An `openid-credential-offer://` link with both `credential_offer=...` and `credential_offer_uri=...` in its query is accepted. A wallet that checks `credential_offer_uri` first fetches the referenced offer and silently ignores the inline one; a wallet that checks `credential_offer` first does the opposite. Neither tells the user that the link was malformed.

## How ProtocolSoup tests it

The hosted wallet accepts offers as `openid-credential-offer://` links, `https` links and pasted JSON. `parseExternalCredentialOfferQuery` and `parseExternalCredentialOfferJSON` both pass the presence of each parameter to the shared `ValidateCredentialOfferEnvelope` check, which returns "credential_offer and credential_offer_uri cannot both be present". The import then fails with HTTP 400 and `invalid_request` before anything is fetched. The same check rejects input that carries neither parameter.

`TestCredentialOfferEnvelopeRejectsBothTransports` calls `ValidateCredentialOfferEnvelope` directly. It asserts an error when both parameters are present and when neither is, and no error for an offer by value alone. It tests the shared check, not the wallet's link parser, so the parser's call to that check is not covered by this test.
