## What this requires

Section 11.1 defines `vp_formats_supported` as "An object containing a list of name/value pairs, where the name is a Credential Format Identifier and the value defines format-specific parameters that a Verifier supports. For specific values that can be used, see Appendix B." The registry sentence is ProtocolSoup's summary rather than spec text. It means using the parameter names Appendix B defines for each format: `sd-jwt_alg_values` and `kb-jwt_alg_values` for `dc+sd-jwt` (B.3.4), `issuerauth_alg_values` and `deviceauth_alg_values` for `mso_mdoc` (B.2.2), `alg_values` for `jwt_vc_json` (B.1.3.1.3), and `proof_type_values` and `cryptosuite_values` for `ldp_vc` (B.1.3.2.3).

For `mso_mdoc` the values are COSE algorithm identifiers, which are integers. Appendix B.2.2 works through an example in which an IssuerAuth "alg header with value -7 (which stands for ECDSA with SHA-256 in [IANA.COSE])" matches an `issuerauth_alg_values` element of -7.

## Why it exists

An mdoc is a COSE structure, and its IssuerAuth and DeviceAuth headers carry integer `alg` values. Appendix B.2.2 matches the metadata against those headers, so the JOSE name `ES256` never equals the integer -7 and the constraint cannot be evaluated. Field names matter in the same way, because Section 11.1 also says "The Wallet MUST ignore any unrecognized parameters." A misnamed field is not an error. It is dropped, and the wallet sees no algorithm constraint at all.

## What non-compliance looks like

A verifier publishes `"mso_mdoc": {"issuerauth_alg_values": ["ES256"]}`, so no IssuerAuth header can match the string. Or it publishes a field name OpenID4VP 1.0 does not define, such as `alg_values_supported`, which a 1.0 wallet ignores, so the verifier's algorithm policy never reaches the wallet.

## How ProtocolSoup tests it

`defaultVPFormatsSupported` (`backend/internal/protocols/oid4vp/handlers.go`) fills `client_metadata.vp_formats_supported` when the create request does not supply its own value. The same map is published in the `verifier_attestation` metadata document. It sets `sd-jwt_alg_values` and `kb-jwt_alg_values` to `["ES256"]` for `dc+sd-jwt`, and `issuerauth_alg_values` and `deviceauth_alg_values` to `[-7]` for `mso_mdoc`. For the W3C formats it uses the 1.0 names: `alg_values` (`ES256`, `RS256`, `EdDSA`) for `jwt_vc_json`, as Appendix B.1.3.1.3 defines, and `proof_type_values` (`DataIntegrityProof`) for `ldp_vc`, as B.1.3.2.3 defines. `jwt_vc_json-ld` is a Credential Format Identifier from OpenID4VCI 1.0 that the verifier accepts in DCQL, but OpenID4VP 1.0 defines no metadata parameters for it, so its entry is an empty object rather than invented fields.

`TestRequestObjectContainsClientMetadataWithVPFormats` decodes a created request object. It asserts that `client_metadata.vp_formats_supported` is present, that it has keys for `dc+sd-jwt`, `jwt_vc_json`, `jwt_vc_json-ld` and `ldp_vc`, and that the `mso_mdoc` entry's `issuerauth_alg_values` and `deviceauth_alg_values` are each exactly the number -7. It also asserts that `jwt_vc_json` carries only a non-empty `alg_values`, that `ldp_vc` carries only a non-empty `proof_type_values`, and that `jwt_vc_json-ld` is an empty object, so a draft `*_supported` name would fail the test.
