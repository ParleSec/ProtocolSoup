## What this requires

When the issuer returns a `notification_id` and advertises `notification_endpoint`, the Wallet tells the issuer what happened to the Credentials. Section 11.1 defines the events. `credential_accepted` "is to be used when the Credentials were successfully stored in the Wallet", `credential_deleted` "is to be used when the unsuccessful Credential issuance was caused by a user action", and "In all other unsuccessful cases, credential_failure is to be used."

The registry records this as a SHOULD for ProtocolSoup's hosted wallet. The specification's own wording is weaker. Section 11 says "Support for this endpoint is OPTIONAL", and Section 11.1 says "If the Wallet supports the Notification Endpoint, the Wallet MAY send one or more Notification Requests per notification_id value received."

## Why it exists

Section 11 gives the purpose: the events "enable the Credential Issuer to take subsequent actions after issuance." It also warns that "The Issuer cannot assume that a notification will be sent for every issued Credential since the use of this Endpoint is not mandatory for the Wallet." An issuer that wants to know whether a Credential reached storage has no other signal to rely on.

## What non-compliance looks like

A Wallet that never calls the Notification Endpoint leaves the issuer unable to tell an accepted Credential from one that was dropped. That is not a protocol violation, because the endpoint is optional. A Wallet that does call it but sends a notification under the wrong Access Token, or sends a made-up `notification_id`, gets `invalid_notification_id`.

## How ProtocolSoup tests it

After a Credential is bound to the wallet, `notifyCredentialAccepted` in `cmd/walletharness/main.go` runs if both a `notification_id` and a notification URL are present. It POSTs `{"notification_id": ..., "event": "credential_accepted"}` as `application/json` with the issuing Access Token. When the token is DPoP-bound it adds a DPoP proof and retries once on `use_dpop_nonce`. If storage fails, the harness returns the error to its caller and sends no notification, so it never sends `credential_failure` or `credential_deleted`.

`TestNotifyCredentialAcceptedUsesNotificationBinding` runs the call against a local test server. It asserts that the `Authorization` header is `Bearer access-1` and that the body carries `notification_id` `notification-1` with `event` `credential_accepted`. It covers the success outcome only.
