## What this requires

The single-use rule comes from Section 4.1.1, where `pre-authorized_code` is defined: "This code MUST be short lived and single use." Section 6.1 sets the Token Request rule for `tx_code`: "This value MUST be present if a tx_code object was present in the Credential Offer (including if the object was empty)."

Section 6.3 maps the failures to error codes. `invalid_request` covers both "The Authorization Server does not expect a Transaction Code in the Pre-Authorized Code Flow but the Client provides a Transaction Code" and the case where one is expected but not provided. `invalid_grant` covers "The Authorization Server expects a Transaction Code in the Pre-Authorized Code Flow but the Client provides the wrong Transaction Code."

## Why it exists

Section 13.6.1 explains the risk: "The Pre-Authorized Code Flow is vulnerable to the replay of the Pre-Authorized Code, because by design, it is not bound to a certain session". A QR code can be photographed over a shoulder or forwarded. Single use limits the code to one redemption, and the Transaction Code binds that redemption to someone who received the code through a second channel.

The two error codes tell the Wallet different things. `invalid_request` means the request was the wrong shape for this offer. `invalid_grant` means the code or the Transaction Code was wrong.

## What non-compliance looks like

Two Wallets, or one Wallet and an attacker, post the same `pre-authorized_code` at the same time, and both receive tokens because the check and the update are not atomic. Other failures are an issuer that returns `invalid_grant` for a missing `tx_code`, or that silently ignores a `tx_code` the offer never asked for.

## How ProtocolSoup tests it

`handlePreAuthorizedTokenGrant` in `handlers.go` returns `invalid_grant` for an unknown, already exchanged or expired code; offers expire after 15 minutes. A missing required `tx_code` gets `invalid_request` ("tx_code is required"), an unexpected one gets `invalid_request` ("tx_code was not expected"), and a wrong one gets `invalid_grant` ("invalid tx_code"), all with HTTP 400. The supplied value is compared with `subtle.ConstantTimeCompare`, so response timing does not reveal how much of the code matched; only its length, which the offer's `tx_code` object already publishes, can affect the timing. Under the plugin mutex, the handler re-reads the offer, marks it exchanged and deletes the code mapping before minting the token. A concurrent loser gets `invalid_grant` ("pre-authorized code has already been exchanged").

`TestPreAuthorizedGrantRejectsUnexpectedTxCode` sends `tx_code` for an offer without one and asserts 400 `invalid_request`. `TestPreAuthorizedGrantDistinguishesMissingAndWrongTxCode` asserts `invalid_request` for a missing value and `invalid_grant` for a wrong value on an offer that requires one. `TestPreAuthorizedGrantExchangeIsAtomic` sends two concurrent Token Requests with the same code and asserts exactly one 200 and one 400. It does not check the loser's error code.
