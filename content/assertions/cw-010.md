## What this requires

Section 13.5: "The Wallet MUST consider the parameter values in the Credential Offer as not trustworthy, since the origin is not authenticated and the message integrity is not protected." It continues: "Therefore, the Wallet MUST perform the same validation checks on the Credential Issuer as it would when initiating the flow directly from the Wallet."

An offer is a hint about where to start, not evidence about who the issuer is. Everything the wallet relies on (endpoints, keys, supported configurations) has to come from the issuer's own metadata and pass the same checks as when the user typed the issuer identifier in.

## Why it exists

The section gives the reason itself: "The Credential Issuer is not considered trustworthy just because it sent the Credential Offer." and "An attacker might attempt to use a Credential Offer to conduct a phishing or injection attack." A QR code or deep link can be produced by anyone, so an offer that names a convincing `credential_issuer` proves nothing about who built it.

## What non-compliance looks like

A wallet that skips metadata validation for offers it receives, for example taking token or credential endpoints from the offer, or proceeding when the fetched metadata's `credential_issuer` differs from the one in the offer. Another form is using the offer's `authorization_server` value without checking that it appears in the metadata's `authorization_servers` array, which Section 4.1.1 requires.

## How ProtocolSoup tests it

In the hosted wallet, offer-initiated and wallet-initiated issuance share `resolveExternalIssuerMetadata`. It fetches `/.well-known/openid-credential-issuer` under the wallet's outbound URL policy, requires `credential_issuer` to match the identifier the metadata was fetched for, and requires a `credential_endpoint`. Authorization Server metadata must report an `issuer` matching the server it was fetched for, or the wallet stops with `discovery_issuer_mismatch`. A configuration from the offer is used only if the metadata describes it. An `authorization_server` hint on the grant the wallet will run must match one of the metadata's `authorization_servers` exactly, or the wallet stops with `invalid_request`; a matching hint narrows the choice only when the metadata lists more than one server, and never adds a server the metadata did not list.

`TestMetadataCredentialIssuerMismatchRejection` asserts that `sameURLIdentifier` matches only identical strings, and rejects pairs that differ by host, trailing slash, letter case, an explicit default port or percent-encoding. `TestOfferAuthorizationServerHintMustMatchMetadata` asserts that a listed hint selects only that server, that a matching hint leaves a single-entry list unchanged, and that the wallet stops for an unlisted server, a trailing-slash variant, metadata that lists no servers, and a single entry that differs. Neither test drives a full offer import, so they do not show end to end that the offer path and the wallet-initiated path run the same validation.
