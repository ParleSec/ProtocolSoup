## What this requires

HAIP 1.0 Section 4.4.1 lists "Additional rules apply when using the format defined in Appendix E of [OIDF.OID4VCI]". Three of them are covered here. The first: "the public key certificate, and optionally a trust certificate chain excluding the trust anchor, used to validate the signature on the Wallet Attestation MUST be included in the x5c JOSE header of the Client Attestation JWT". The second: "Wallet Attestations MUST NOT be reused across different Issuers. They MUST NOT introduce a unique identifier specific to a single Wallet instance. The subject claim for the Wallet Attestation MUST be a value that is shared by all Wallet instances using the present type of wallet implementation." The third: "if applicable, the client_id value in the PAR request MUST be the string in the sub value in the client attestation JWT."

## Why it exists

For the subject rule HAIP points to OpenID4VCI Section 15.4.4, which sits in that specification's privacy considerations. The plain consequence: an attestation that is reused, or that carries a per-instance identifier, lets Issuers that compare notes link one user's wallet across services. The `x5c` rule lets an Issuer validate the attestation against its own trust anchor without fetching keys. Tying `client_id` to `sub` stops a wallet from authenticating as one client while claiming to be another.

## What non-compliance looks like

The attestation `sub` is a per-install UUID. One long-lived attestation JWT is sent to several Issuers. The PAR form says `client_id=wallet-app` while the attestation says `"sub":"com.example.wallet"`. Or `x5c` is missing, or ends with the root CA.

## How ProtocolSoup tests it

The hosted wallet's `buildClientAttestationJWT` signs an ES256 `oauth-client-attestation+jwt`. Its `iss` comes from `WALLET_CLIENT_ATTESTATION_ISSUER`, and its `sub` is the attested client ID from `WALLET_OID4VCI_ATTESTED_CLIENT_ID`, a deployment-wide value with default `protocolsoup-wallet`. It expires after five minutes, and `cnf.jwk` holds a client instance key generated per issuance session. A new attestation is minted for every PAR and token request, and on the HAIP path the PAR and token `client_id` is that same attested ID. The `x5c` is copied verbatim from `WALLET_CLIENT_ATTESTATION_ATTESTER_JWK_JSON`, and loading fails if the array is absent. No code strips a trust anchor, so the trust-anchor exclusion depends on what the operator provisions.

`TestClientAttestationIssuerEnvOverride` asserts the `iss` override and its default. `TestHAIPAttestationJWTBuildersUseExpectedHeaders` asserts the attestation and PoP `typ` values, that the attestation `sub` equals the client ID, and that the PoP `iss` equals it too. It also checks the key attestation and proof headers, and that the HAIP proof's `iss` is the attested client ID, that it carries no `sub`, and that it omits `iss` when there is no client ID. It passes a chain that includes the root and does not inspect `x5c`. `TestPushAuthorizationRequestFetchesChallengeEndpoint` asserts that PAR fetches the challenge once and that the PoP carries it. `TestBuildClientAttestationPoPJWTIncludesChallengeClaim` asserts the `challenge` claim. No test checks the PAR `client_id` against `sub`, per-Issuer freshness, or the trust-anchor exclusion.
