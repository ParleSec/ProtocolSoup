## What this requires

This is check 3 of RFC 9449 Section 4.3. Section 4.2 says "The payload of a DPoP proof MUST contain at least the following claims": `jti`, `htm`, `htu` and `iat`. Two more become required by context: `ath` "When the DPoP proof is used in conjunction with the presentation of an access token in protected resource access", and `nonce` when the server has provided a `DPoP-Nonce` header.

A proof that lacks any claim required in its context is invalid, however good its signature is. The server does not fill in a default or skip the check that the missing claim would have fed.

## Why it exists

Each claim carries one of the proof's guarantees. `jti` is what replay detection keys on (Section 11.1), `htm` and `htu` tie the proof to one method and one URI, `iat` bounds how long it is accepted, and `ath` ties it to one access token. A verifier that only checks the claims that happen to be present can be bypassed by leaving a claim out, so the guarantee that claim provides disappears without any check failing.

## What non-compliance looks like

A server that checks `htu` only "if present" accepts a proof with no `htu`, and that proof can then be sent to any endpoint that trusts the same key. A server that does not insist on `jti` cannot detect replays of that proof at all.

At a token endpoint the correct response is HTTP 400 with `invalid_dpop_proof` (RFC 9449 Section 5).

## How ProtocolSoup tests it

`dpop.ValidateProof` requires `jti` to be a non-empty string and `iat` to be a NumericDate. A missing `htm` fails the comparison with the request method and a missing `htu` fails URI normalisation, so neither can be absent. When the caller passes the access token, which every resource endpoint does, a missing `ath` fails the hash comparison. When a nonce issuer is configured, an absent `nonce` is never valid and the endpoint answers with a `use_dpop_nonce` challenge.

`TestValidateProofRejectsMissingJTI` deletes `jti` from an otherwise valid ES256 proof and asserts that validation returns an error. It is the only registry test for this row: no test removes `htm`, `htu` or `iat` on their own, so the other required claims are covered by the code paths above rather than by a dedicated test.
