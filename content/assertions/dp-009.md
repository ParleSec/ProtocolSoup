## What this requires

This is check 10 of RFC 9449 Section 4.3. When a server has given the client a nonce in a `DPoP-Nonce` response header, the proof's `nonce` claim must carry that value. Section 8 says: "If the nonce claim in the DPoP proof does not exactly match a nonce recently supplied by the authorization server to the client, the authorization server MUST reject the request." Section 11.3 closes the gap of leaving the claim out: "A server MUST NOT accept any DPoP proofs without the nonce claim when a DPoP nonce has been provided to the client."

The rejection uses the error code `use_dpop_nonce` and can carry a fresh `DPoP-Nonce` for the retry: HTTP 400 at an authorization server (Section 8), HTTP 401 with a `DPoP` challenge at a resource server (Section 9).

## Why it exists

Section 11.2 explains that a client, or the user controlling it, can pre-generate proofs "arbitrarily far into the future" by choosing `iat`, and copy them to a machine without the key. A nonce the server chose at a time of its choosing cannot be predicted, so a matching nonce shows the proof was signed after the server issued it.

## What non-compliance looks like

A server that sends `DPoP-Nonce` but accepts proofs with no `nonce` claim, or with any value, gets no protection from the mechanism: a pre-generated proof still works. Section 11.3 calls this a nonce downgrade.

## How ProtocolSoup tests it

Nonces are off by default. `SHOWCASE_DPOP_NONCE_REQUIRED` turns them on for the OAuth 2.0 and OID4VCI token endpoints and the OID4VCI pushed authorization request endpoint, and `SHOWCASE_DPOP_RESOURCE_NONCE_REQUIRED` turns them on, as a separate nonce space, for the OAuth 2.0 protected resource and the OID4VCI resource endpoints. Each space is shared by all clients of that endpoint role, not issued per client. After the proof passes every other check, the endpoint asks its `NonceIssuer` whether the `nonce` claim is the current or immediately preceding value, compared in constant time. An empty or unknown value gets `use_dpop_nonce` with a new `DPoP-Nonce` header.

`TestValidateProofRequiresNonceWhenInForce` signs a proof with a `nonce` claim and asserts that `dpop.ValidateProof` accepts it when the `RequiredNonce` option holds the same value and rejects it when it holds a different one. No endpoint sets `RequiredNonce`, so this test exercises a code path production does not use. The production path is covered by endpoint tests not listed on this row, such as `TestTokenEndpointChallengesMissingNonceWhenRequired` and `TestTokenEndpointForeignOrStaleNonceIsRejectedAsFreshChallenge`, which assert HTTP 400 `use_dpop_nonce` with a `DPoP-Nonce` header.
