## What this requires

With `request_uri_method=post`, the wallet fetches the Request Object by POSTing to the `request_uri`, optionally sending `wallet_metadata` and `wallet_nonce`. Section 5.10 defines `wallet_nonce` and says "When received, the Verifier MUST use it as the wallet_nonce value in the signed authorization request object." The nonce has to sit inside the signed claims, so the verifier signs the object after adding it. Section 5.10.1 sets the wallet's side: "if the Wallet passed a wallet_nonce in the POST request, the Wallet MUST validate whether the request object contains the respective nonce value in a wallet_nonce claim. If it does not, the Wallet MUST terminate request processing."

Serving the identical object for a repeated POST with the same nonce, and refusing a different nonce, are ProtocolSoup's choices; the spec does not require either. The section this row cites, 5.10.2, covers what happens next: "If the Verifier responds with any HTTP error response, the Wallet MUST terminate the process."

## Why it exists

Section 5.10 gives the purpose of the parameter: wallet_nonce is "A string value used to mitigate replay attacks of the Authorization Request." A Request Object signed with a nonce the wallet chose a moment earlier cannot be one captured from another exchange and replayed. ProtocolSoup binds the first nonce it receives so that one request session belongs to one retrieval. A second party that POSTs a different nonce cannot obtain a freshly signed copy of the same request, carrying the same `state` and `nonce`, for itself.

## What non-compliance looks like

A verifier returns the object it signed at creation time, without `wallet_nonce`, and a conformant wallet terminates. A verifier adds `wallet_nonce` to an object it does not sign again, so the signature no longer verifies. A verifier signs again on every POST with whatever nonce arrives, so the same request session can be bound to any number of wallets.

## How ProtocolSoup tests it

`handlePostAuthorizationRequest` (`backend/internal/protocols/oid4vp/handlers.go`) accepts POST only for requests created with `request_uri_method=post`. Otherwise it returns 405 `invalid_request` with `Allow: GET`, and a GET to a POST-only request returns 405 `invalid_request` with `Allow: POST`. Section 5.10 makes `wallet_nonce` OPTIONAL, so a POST without one is answered with the stored request object and binds nothing; a later POST may still bind a nonce. A supplied nonce may be at most 256 characters. If `wallet_metadata` is present, it must be a JSON object of at most 32 KiB. On the first valid POST the handler adds `wallet_nonce` to the stored claims, signs the object again under the same Client Identifier Prefix, and stores it. A POST with the same nonce returns those exact bytes. A different nonce, or none, after binding fails with 400 `invalid_request` and `wallet_nonce does not match the first request`. Successful responses carry `Content-Type: application/oauth-authz-req+jwt` and `Cache-Control: no-store`.

`TestAuthorizationRequestPOSTBindsWalletNonceAndIsSafelyRepeatable` creates a request with `request_uri_method=post` and asserts that GET returns 405. It then POSTs `wallet_nonce=wallet-nonce-123` and asserts 200 and a `wallet_nonce` claim with that value, asserts that a second POST with the same nonce returns byte-identical content, and asserts that a different nonce returns 400. The test decodes the object without verifying its signature, so it shows the claim is present but not that the new signature covers it, and it does not check the response media type. `TestAuthorizationRequestPOSTWithoutWalletNonce` POSTs without a nonce and asserts 200, `Content-Type: application/oauth-authz-req+jwt`, no `wallet_nonce` claim, and identical bytes on a repeat. It then asserts that a later nonce still binds, and that a nonceless POST after binding returns 400.
